# 段落と論の運び

`SKILL.md` の段落レベル。人が読む文すべてに適用する。本文、表のセル、callout、完了メッセージ。

ここにあるのは言語を問わず成り立つ規則だけである。文と語のレベルは言語ごとに違うので、`japanese.md` と `english.md` にある。出力言語の参照を、このファイルと一緒に読む。

出典は prism-data-labs-agent の `write-analysis-report/references/prose-style.md`。分析固有の例（未実行のクエリ、指標の因果機構、推奨）はリサーチ向けに差し替えた。

## 1. 段落

- 一段落に話題はひとつ。段落の書き出しだけを拾って読んでも論が追えること。
- 書き出しの文で、何の段落かが分かるようにする。じっくり読むべき段落かどうかが、そこで判断できる。
- 前の段落との関係が自明でないときは、つながりの語で始める。関係の説明なしに新しい主語で始まる段落は、別の文書の一部に見える。
- 一方向に論じる。予想される誤読を先に否定してから、正しい説明を置く。結論を述べてから撤回しない。
- 「詳しくは後述する」は段落や節の末尾に置く。論の途中に置かない。

## 2. 論の精度

- **別のものを「同じ」にまとめない。** 似た定義がふたつあるなら、ふたつあると書く。
- **複数の要因をひとつにしない。** 三つが効いているなら三つ書き、大きさの比が取れるなら付ける。
- **仕組みまで書く。** 「欠測が直訪シェアを膨らませる」は仕組み、「欠測が影響する」は仕組みではない。リサーチなら「Hickey の言う複雑さは、部品の数ではなく互いに編み込まれていることを指す」が仕組みで、「三人が複雑さについて論じている」は仕組みではない。
- **検出範囲を言いすぎない。** 条件を書く。「`order_id` が一致する重複を拾う」であって「重複を拾う」ではない。
- **例が主張の全部を支えているか確かめる。** 一部しか支えていないなら、主張のほうを狭める。
- **意味のある留保は残す。** 「おそらく」は未確認の印である。自信ありげに消すのは事実の書き換えになる。意味のない留保を削るのは文体の調整であって、これは構わない。
- **予告した節は実際に書く。**
- **語は使う前に定義し、範囲を付ける。** 一度決めたら、曖昧な言い換えに戻らない。

## 3. 読者の負担

- 新しい考えはひとつずつ出す。概念とその例外を一文に詰めると、読み返される。
- 一度しか出てこない識別子（ファイル名、内部ID、検索クエリ）を本文に置かない。ものを説明し、識別子は付録に送る。
- 抽象語は、初出のところで括弧に具体例を添える。
- 概念を出すときは、どういう種類のものかを先に言い、働きは後に書く。
- 媒体ごとに役割を分ける。図は構造、表は値、散文はそこから何が言えるか。図の中身を一ノードずつ文で説明し直さない。
- 「これ」「その差」の指す先が、その文だけで分かるようにする。

## 4. 出典の書き方

**`[n]` 形式の番号引用を使う。** 本文に出典名を書き込まず、文末に `[3]` を置く。番号は付録の一覧に対応させる。

これは体裁の話ではなく、文の主語を守るための仕組みである。番号引用がないと、書き手は出典名を主語にするしかなくなり、レポートが書誌になる。

```
NG: Validatar の「10 Data Quality Tests」は、PIT/Bridge の参照整合性の欠落が
    エラーではなくレポート欠損として現れると書く。
OK: PIT/Bridge の参照整合性が欠けると、エラーにならずレポート上の欠損として出る [25]。

NG: Scalefree の Business Vault 解説は、Raw にはソースに近い硬いルールのみを置き、
    BV にソフトルールを載せるとする。
OK: 硬いルールは Raw に、軟いルールは Business Vault に置く [11][12]。
```

規則は三つ。

- **出典名を文の主語にしない。** 主語は論じている対象の側に置く。
- **「〜は述べる」「〜は書く」「〜は指摘する」で文を終わらせない。** 事実として書き、番号を付ける。
- **出典名を本文に出すのは、その人や組織の立場そのものが論点のときだけ。** 「Brooks は本質と事故を分けた」は、Brooks が誰であるかが主題なので正しい。「Megha GD の BigQuery 銀行事例は〜と書く」は、読者にとって固有名に意味がないので不要である。

同じことを言う出典が複数あるなら、一文にまとめて番号を並べる。`[11][12][15]`

## 5. 声

- 行為者を主語にする。「取り込みステップが顧客IDのない行を落とす」は、「顧客IDのない行は落とされる」より良い。
- 読者の人物像を作らない（「二年目のアナリストを想像してほしい」）。役割名を使う。制作者、聞き手、読者。
- 「あなた」より役割名。
- その分野が実際に使っている語を選ぶ。それらしく聞こえるだけの言い換えに置き換えない。
- 術語を、術語でない意味に流用しない。

## 6. 抑制

レトリックは読者の注意を消費する。論が折れるところでだけ使う。

- 修辞疑問と間合いは、本当に折れる点に置く。
- 一行の断言を、癖で独立した段落にしない。
- 発見を、起こりうる惨事の列挙で盛り上げない。
- 重要性を宣言しない（「ここで重要なのは…」）。置く場所で示す。
- 「AではなくB」を連打しない。

## 7. 見たら消す埋め草

長さだけが増える句である。

| 種類 | 日本語 | 英語 |
|---|---|---|
| 予告と要約 | 本章では〜を扱う／ここでは〜について見ていく／まとめると／要するに／〜に他ならない | this section covers, in summary, in other words |
| 空の形容 | 不可欠／核心的／鍵となる／多角的／包括的／さまざまな | essential, core, key, multifaceted, comprehensive |
| 空の動詞 | 掘り下げる／言語化する／触れる／言及する | dig into, articulate, touch on, mention |
| 接続の詰め物 | 〜において／〜という側面から／「さらに」の連打 | in terms of, from the perspective of, stacked furthermore |
| 根拠のない弱め | 根拠のない「〜と言えるだろう」「非常に」「かなり」 | it could be said that, very |

## 8. 翻訳調と擬人

英語の比喩をそのまま日本語にすると、技術文書では雑音になる。仕組みを、知ったり欲しがったりする主体にしない。

| ではなく | こう書く |
|---|---|
| ベクトルが嗜好を運ぶ | 嗜好はベクトルとして表される |
| この問いは開かれている | これは未解決である |
| データが教えてくれる | データから〜が分かる |
| モデルがスタイルを知っている | モデルの出力は文体として一貫している |
| この指標は有望だ | その指標の何が使えるのかを書く |

見分け方は、初めて読む人がその語を辞書どおりの動作として思い浮かべるかどうかである。思い浮かべるなら翻訳調を疑う。行為者と対象を平易な語で名指せるなら、そちらを書く。

日本語で書くときは `japanese.md` 第1部を読む。置き換え表と検出手順がそこにある。

## 9. 重複

- 主張は一度だけ書く。言い換えて繰り返すのは強調ではなく、存在しない区別を読者に探させる行為である。
- 図や表の中身を散文で繰り返さない。そこから何が言えるかを一文だけ足す。
- 隣り合う並列の事実は一文にまとめる。
- つなぐだけの文、評価するだけの文を書かない。
- 想像上の読者との対話を演じない。
- 自分の立場を弁明したり、形式を詫びたりしない。
- 概念や文書名を、必要になる前に出さない。
- 確定したことを、弱い動詞で不確かに見せない。

## 10. 読者への正直さ

- 作った例なら、読者が見抜く前にそう書く。
- 自明な反論は先回りして認める。
- 主張は、読者が辿れる出典に根ざす。書き手の断言だけに根ざさない。
- 未確認のことを、確認済みと同じ口調で書かない。一次資料を読んでいないなら、文がそれを示すこと。
- 提言しない。誰が・いつまでに、は分析レポートの仕事であり、このスキルの仕事ではない。
