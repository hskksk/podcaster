# レポートの構造

`SKILL.md` ステップ3の詳細。本文を書き始める前に読む。

分析レポート（prism `write-analysis-report`）から情報設計を借り、次は外した。待っている判断、数値必須の主結果、確度付きの因果、提言。残したのは三層構成、概要が本体であること、調査順で章立てしないこと、全体像を図で置くことである。

さらに、実レポート2本の計測（`podcast-research` 版と `podcast-research2` 初版の比較）から、**日本語で書くときに限って分析レポートの規則を反転させた箇所が三つある**。見出し・出典・太字である。理由は各節に書いた。

その次の改訂で、旧スキルの固定目次を完成原稿から外しすぎたことが分かった。図と主張見出しは残し、**概要に文書の位置づけを戻し、経緯を本文の固定枠に戻す。**

## 書く前に決める6つ

失敗の典型は、調べながら書くことである。検索のたびに見出しが増え、完成原稿が発見順になる。項目が多すぎるのに、どれが支えなのか分からない。

段落を書く前に、次の6つを一文ずつ決める。

1. **問い。** 読者の言葉で書く。テーブル名や検索クエリの言葉で書かない。
2. **答え。** 一文にする。書けないなら調査が終わっていない。箇条書きでは代用できない。
3. **軸。** 細部がひとつのものに見える理由。年表でも、対立する定義でも、ひとつの仕組みでもよい。軸のない答えは目録になる。
4. **三つの主張。** 答えを支え、互いに重ならない。
5. **扱わない範囲。** 調べたが本文を支えないもの。付録に送る。
6. **経緯。** 主張が今の形になるまでの一文。書けないなら歴史を調べていない。

概要を1〜5から先に書く。本文を先に書いて概要を後回しにすると、概要が各節の要約になり、答えにも位置づけにもならない。6は `背景・歴史` の見出しになる。

概要にはもうひとつ、**この文書の位置づけ**を入れる。問いと答えが中身なら、位置づけは「何の文書としてそれを述べるか」である。分析レポートの「誰がいつまでに決めるか」という目的文とは別物なので、外さない。

## 三層

どの材料がどの層に入るかを、書く前に決める。

| 層 | 中身 | 分量 | 誰が読むか |
|----|------|------|----------|
| **L1 概要** | 答え・軸・位置づけ（何を扱い、何が目的か、なぜ今か）・調査範囲 | 5〜8文 | ここだけ読んで、この文書が何の文書かと、ポッドキャストの角度を決める人 |
| **全体像** | 主張の関係を辺に載せた図 | テーマが3つ以上なら必須 | 答えの構造だけ先に見たい人 |
| **背景・歴史** | 主張が今の形になるまでの筋 | テーマの前。年表の全項目は付録 | 主張を時代の中で読みたい人 |
| **L2 本文** | 答えを支える4〜8のテーマ | 主張を言い切るだけ | 答えが証拠に足りるか確かめる人 |
| **L3 付録** | 出典一覧、年表の全項目、人物、隣接分野、未確認点、使わなかった調査の枝 | 上限なし | 再現・監査・次の調査をする人 |

三層を体裁ではなく実体にするのは、次の三つである。

- **概要は本体であって予告ではない。** 概要だけで答えと、この文書の位置づけが言えること。
- **概要に前方参照を置かない。** 「詳細は第3節」は層を壊す。数そのものを概要に入れる。
- **主張が使わないものは付録へ。** 面白いだけでは本文に残さない。ただし経緯の筋は主張の前提なので、付録に送らない。

## L1 概要 — 答えと、この文書の位置づけ

概要はレポート全体の縮小版である。ここで読むのをやめた人が、論そのものと、**この文書が何の文書か**を言えること。

**長さは5〜8文、2〜4段落。** 初版は8〜12文、次の改訂は4〜6文だった。4〜6文に縮めたとき、答えは残ったが位置づけが落ちた。8〜12文には戻さない。各節の要約を並べるためではなく、位置づけの1〜2文を足すために枠を少し戻す。

分析レポートの6スロット（背景・目的・見取り図・範囲・枠組み・主張）のうち、**主張・範囲・枠組み（軸）は概要に残し、目的は位置づけとして残し、背景は次の節へ出し、見取り図は図にする。** 全部を見出しなしの短い要旨へ圧縮すると、目的と背景が消える。

五つの規則がある。

- **1文目に、読者が知っている具体名詞を置く。** 「Data Vault 2.0 は Hub・Link・Satellite という型と、挿入のみの履歴管理で知られる」は良い。「本稿は運用知を三つの主張に整理する」は悪い。
- **答えと軸を先に書く。** 方法（調べた、横断した、整理した）ではなく、分かったことを書く。
- **位置づけを1〜2文入れる。** 何を扱い、何が目的で、なぜ今読むか。文書の種類と目的であって、書き方の説明ではない。
- **スキル内部の語を出さない。** 「見取り図」「枠組み」「射程」「骨格」「L1」は作業用の語である。読者はこのスキルを読んでいない。`japanese.md` 第1.9節を見る。
- **調査範囲は概要に入れる。** 末尾の注意書きに送らない。いつの資料か、何を扱っていないかは、冒頭で分かるべきである。

見出しは `## 概要` にする。見出しなしの要旨はやめる。目次に「概要」が出ないと、位置づけのスロットが見えない。`## 概要` はスロット名なので、主張のダッシュは付けない（`## 全体像` と同じ）。

### 位置づけと、書いてはいけないメタ

「レポート自身について語るな」は、書き方の話を禁じた規則であって、文書の位置づけまで禁じたものではなかった。実レポートでは後者まで落ちた。

| 種類 | 例 | 判定 |
|---|---|---|
| 位置づけ（必要） | ここでは三代の定義を横断する。目的は「複雑さ」を、計測指標と引き継ぎやすさの両方から使える語彙にすることだ | 何を扱い、何が目的か |
| 位置づけ（必要） | なぜ今読む価値があるか。書くこと（easy）は安くなったが、編むこと（complex）のコストは下がっていない | なぜ今か |
| 方法メタ（禁止） | 本稿は運用知を三つの主張に整理する | 書き方を説明している |
| 方法メタ（禁止） | 読者が持ち帰る理解は次のとおりである | 内部語。中身を書け |
| 前方参照（禁止） | 詳細は第3節で述べる | 概要が予告になる |

「本稿は」で始めてはいけない、は1文目の規則である。位置づけの文で「ここでは」「扱うのは」「目的は」を使うのは構わない。

### 例

```markdown
## 概要

ソフトウェアが難しいのは、コードの行数やテーブルの枚数のせいだけではない。
難しいのは、人間が一度に少数しか考えられないのに、システムは「一緒に考えねばならない範囲」を
勝手に広げてくることだ。この直観を言葉にした中核は、Brooks（1986）、
Moseley & Marks（2006）、Hickey（2011）の三代である。

三人に共通するのは、複雑さを部品の個数ではなく認知と変更のコストとして扱ったことだ。
違うのは、Brooks が「本質は残る」と警告したのに対し、後の二人は
「残っていると思っているもののかなりは、まだ切り出せる」と見たことである。

ここではこの三代を軸に、同じ「複雑さ」という語が別の定義を同居させてきた経緯を扱う。
目的は、計測可能なコード指標と、引き継ぎやすさの感覚とを取り違えない語彙を残すことだ。
生成AIは書くこと（easy）を安くしたが、編むこと（complex）のコストは下がっていない。

対象は1986年から2011年の一次資料と、それを扱った二次文献である。
循環的複雑度などの計測指標のカタログは扱わない。
```

4段落。1文目から Brooks 以前の直観が出ている。3段落目が位置づけ（何を扱い、何が目的か、なぜ今か）。「本稿は三つの主張に整理する」も「見取り図」も出てこない。

旧スキル版の概要は、位置づけと「なぜ今か」を持っていた。改訂版の要旨は答えと範囲だけになり、文書が何のために存在するかが消えた。戻すのは前者である。

## L2 本文 — 見出しに主張させる

**ここが初版から最も大きく変わった点である。**

初版は「見出しは対象を名指すだけにし、結論は各節の第一文へ置く」という規則（単独見出しテスト）を持っていた。これは英語の分析レポート由来で、英語では見出しが大文字で始まり語間に空白があるため、見出しと第一文がひとつの塊として目に入る。**日本語では成立しない。** 見出しと本文の距離が遠く、第一文まで目が降りない。結果、目次が抽象名詞の羅列になり、読者はどの節に何があるか分からなくなる。

日本語では、**見出しに結論を上げる**。

### 見出しの形

```
## <番号>. <対象の名詞句> — <主張の断片>
```

```
OK: ## 2. 消費層は必須 — Raw Vault を BI に直結しない
OK: ## 3. ハッシュ契約 — 静かに壊れて JOIN が消える
OK: ## 7. チーム規模 — 人数とソース数が手法の適否より先に効く

NG: ## レイヤ規律と二重時間          ← 中身を読むまで何も分からない
NG: ## モデリングとパイプラインの罠  ← 同上
NG: ## PIT と Bridge が買うもの      ← 直訳（japanese.md 1.3）
```

番号を振る。読者が「7番の話」と参照でき、付録との対応も付けやすい。

**目次テスト**: 目次だけを上から順に読んで、サーベイの結論が言えること。言えないなら見出しが弱い。このテストが、初版の単独見出しテストに置き換わる。

### テーマは4〜8、主張は3つ

主張は3つ（±1）に絞る。ただし**主張の数と節の数を一致させない**。初版は「主張ノードと節が一対一」を規則にしたため、本文が3つの大きな塊になり、それぞれ4,000字近くになった。内容は減らず、減ったのは案内標識だけだった。

二段にする。

- **概要と全体像の図が引き受ける主張は3つ。**
- **L2 の見出しは4〜8のテーマ。** どのテーマも3つの主張のどれかに属する。属さないテーマは付録へ送る。
- 図の下の一文で、どのテーマがどの主張に属するかを述べる。「1〜3は層の話、4〜6は時刻の話、7〜8は人の話である。」

これで、主張を絞る効果（散らばらない）と、見出しを増やす効果（探せる）を両立できる。

### 各テーマの契約

1. **第一文が、見出しの主張を条件付きで言い直す。** 見出しは短いので条件が落ちる。第一文で条件を戻す。
2. **続く段落が根拠を述べる。** 一方向に進む。根拠、その読み、予想される反論とその答え。主張 → 反論 → 撤回の順は取らない。
3. **図と表は、それを支える文の直後に置く。** どの文も依存しない図は付録へ。
4. **節末に持ち帰りを一行置く。**

### 節末の持ち帰り

各テーマの最後に、太字のラベルを付けた一行を置く。

```markdown
**運用で分かったこと:** ハッシュまわりは一度壊れると全リンクが静かに切れる。
コードレビューより、CI での機械的検証のほうが割に合う [1][23][25]。
```

ラベルはテーマの性質に合わせて変えてよい。「運用で分かったこと」「現場が書いていること」「ここまでの要点」など。**初版の「この節が見取り図へ足すのは〜である」は使わない。** 直訳であり、内部語を含む（`japanese.md` 1.8, 1.9）。

行動指示で終わらせない。提言はこのスキルの仕事ではない。

### 長い節は内部で割る

- **1,500字を超えた節に `###` を入れる。** 一節あたり小節は2〜4。それ以上に割れるなら、テーマがふたつ入っている。
- **小節は根拠の種類で割る。** 資料が出てきた順でも検索した順でもない。「何が起きるか」「なぜそうなるか」「例外はどこか」「反対の事例」のように、テーマに対する役割で割る。
- テーマの主張は `##` の直下に置く。第一文が主張、その段落までが最初の `###` の前。持ち帰りの一行は、最後の小節の末尾に置く（Markdown では小節を閉じて `##` の水準に戻れない）。

### 列挙が素材のときは表にする

「推論は段落、一覧は表」は、**推論**を箇条書きに潰すなという規則であって、一覧を散文に流し込めという規則ではない。資料が十本あり、それぞれが同じ形の情報（誰が・どこで・何を言ったか）を並べているなら、それは一覧である。

- 同じ列を持つものが四つ以上並ぶなら**表**にする。出典一覧、層ごとの役割、対立する定義の比較。
- 表にしたら、散文にはそこから何が言えるかだけを書く。表の中身を文でなぞらない。

## 出典は `[n]` 番号で

**これも初版から反転した点である。**

初版は「出典の帰属は段落に一度」という規則を置きながら、**引用の仕組みを与えていなかった**。結果、書き手は出典名を文の主語にするしかなくなり、本文220文のうち141文が冒頭に出典名を含む状態になった。禁じた失敗が、代わりの道具がないために実現した。

`[n]` 形式を必須にする。詳しい書き分けは `prose-style.md` 第4節にある。

- 本文に出典名を書かず、文末に `[3]` を置く
- 番号は `## 付録: 出典一覧` の項目に対応させる
- 「〜は述べる」「〜は書く」で文を終わらせない
- 出典名を本文に出すのは、その人や組織の立場そのものが論点のときだけ

実測では、出典名が主題位置に来る文の割合が25%から3%に下がった。

## 全体像を図で置く

概要の直後、背景・歴史の前に図を置く。テーマが三つ以上あるときは必須。順序は `概要 → 全体像 → 背景・歴史 → 番号付きテーマ` である。図を描かないとき（主張がふたつ以下）は、概要の直後に背景・歴史を置く。

見出しは `## 全体像` にする。`## 骨格` は内部語である。

散文で索引を書くと「主張を一行ずつ並べ、最後に関係を一文で述べる」形になり、その最後の一文が最初に落ちる。三行だけ書いて関係を書かない、本文は六節なのに索引は三行のまま、という壊れ方をする。辺そのものが関係になっている図なら、関係は書き忘れようがない。

ノードは6種類。

| タグ | ノードの中身 | 個数 |
|---|---|---|
| **問い** | レポートが答える一文 | 1 |
| **軸** | 細部がひとつに見える理由。主張を束ねるもの | 1 |
| **分かったこと** | 主張を一行ずつ | 3（±1） |
| **答え** | 問いへの答え。主張が収束する先 | 1 |
| **扱わない範囲** | 調べたが本文を支えないもの。破線で鎖から外す | 0〜2 |
| **調査範囲** | いつ・どの資料・どこまで。鎖全体にかかる | 1 |

ノードのラベルに内部語（見取り図・枠組み・射程）を使わない。上の6語は読者が読んで分かる語である。

**主張どうしを結ぶ辺には、関係を示す語を必ず載せる**（「前提になる」「反論する」「条件を課す」「別方向から狭める」）。書けないなら連鎖ではないので、辺を引かず `軸 → 各主張` の並列だけを描く。連鎖か並列かを図の上で言えないなら、主張の切り方がまだ決まっていない。

### 規則

- **どのテーマも、いずれかの主張ノードに属する。** 属さないテーマは付録へ。図の下の一文で対応を述べる。
- **ノードは主張を一行にしたもの。** 見出しのコピーでも、対象の名詞句でもない。40字を超えると折り返して読めなくなるので、超えたら主張を絞る。
- **ここにしかない事実を置かない。** 図は索引であって第三の本文ではない。概要にも本文にもない数字をノードに入れない。
- **図の下に一文を添える。** 関係（連鎖・並列・対比）を述べ、テーマとの対応を書く。図の中身をなぞらない。
- **主張がふたつ以下なら図を描かない。** 二行で足りるものに、描画と横スクロールのコストを払わない。そのときだけ、主張を文書順に並べたリストに関係の一文を添える形でよい。索引なので、`SKILL.md` の「節の本体が箇条書きだけ、は禁止」の例外になる。

## 背景・歴史 — 主張が立つまでの筋

番号付きテーマの前に、経緯の節を置く。見出しは次の形にする。

```
## 背景・歴史 — <経緯の主張>
```

```
OK: ## 背景・歴史 — 危機の診断から、複雑さを認知のコストで測る三代へ
OK: ## 背景・歴史 — 導入記事は増えても、数年回した振り返りは残っていない
NG: ## 背景・歴史
NG: ## 5. 三つの定義が生まれた背景 — 技術と問題の変化
```

最後の NG は、経緯を番号付きテーマのひとつに混ぜた例である。テーマ5として後回しにすると、主張を読んだあとで「なぜこの議論があるか」が来る。順序が逆である。

この節の仕事は、主張を時代の中に置くことである。年号のカタログではない。

- **書くのは筋である。** 誰が、何に応答して、今読者が見る形になったか。旧スキルの「背景・歴史」が果たしていた仕事はこれである。
- **年表の全項目は付録に残す。** 本文の歴史が長くなるのは、日付を全部載せているときである。1,500字を超えたら `###` で割るか、項目を付録へ移す。
- **主張の前提になる経緯だけを残す。** 人物の伝記、隣接分野の年表、本論に入らない起源説は付録。
- **経緯そのものが主題のとき**（人物評伝、制度の成立史）は、番号付きテーマが歴史を引き受けてよい。その場合も `## 背景・歴史 — …` で軸になる一文は残す。短い節でよく、詳細をテーマへ渡す。

旧スキルは歴史を固定枠にしていたので落ちなかった。このスキルは「主張が使わないものは付録へ」を徹底した結果、経緯まで付録の年表になった。主張の整理は残し、経緯の置き場所だけ戻す。

### 例

```markdown
## 背景・歴史 — 危機の診断から、複雑さを認知のコストで測る三代へ

1968年の NATO ソフトウェア工学会議で software crisis という言葉が使われた。
ハードウェアは安く速くなる一方、正しさ・納期・保守が需要に追いつかない、という診断である。
Dijkstra は危機の主因を「マシンが強大になったこと」だとした。貧弱な計算機しかなければ、
プログラミングは穏やかな問題だった。

Brooks は IBM OS/360 を率い、1975年にタール坑の比喩で大規模開発を書いた。
1986年の『No Silver Bullet』が、その危機意識を本質と事故の区別に折った。
2006年の『Out of the Tar Pit』は「残っている複雑さの大半はまだ事故だ」と返し、
2011年の Hickey は単純と簡単を分けた。

並行して、Parnas の情報隠蔽、Yourdon / Constantine の結合度、McCabe の循環的複雑度が
同じ問題を別の語彙で測っていた。本文は三代の定義の違いを扱い、計測指標のカタログは付録に置く。
```

3段落で系譜が言える。Aristotle からの語の借用や銀の弾の題名の由来は、テーマ1の根拠か付録へ送る。

## まとめの節を末尾に置く

本文の最後、付録の前に、番号付きの持ち帰りリストを置く。

```markdown
## まとめ — 運用者が繰り返し書いている10点

1. **情報マートを最初から計画する**（Raw を BI に出さない）[16][19]
2. **ビジネスキーと Hub の設計に時間を使う** — ソースをそのまま写した Vault を避ける [33][34]
3. **ハッシュ規約を機械検証する** [1][23][25]
```

通読しない読者は、概要とここだけを読む。各項目に `[n]` を付け、本文のどのテーマの結論かが辿れるようにする。

これは索引なので、`SKILL.md` の「節の本体が箇条書きだけ、は禁止」の例外である。

## L3 付録

付録は捨て場ではない。本文を通読できる長さに保つための層である。送るもの。出典一覧、年表の全項目、人物、隣接分野、本文が使わなかった調査の枝、長い引用。

**`## 付録: 出典一覧` は必須。** `[n]` の番号順に、著者・題・日付・URL を並べる。形式は `- [1] 著者, [題](URL)（日付）`。

**互いに異なる文献を集める。** 同じ論文の別版、別ページ、それを解説したブログを別番号に分けて本数を稼がない。URL を控えていないものは、別小節「URL を記録していない出典」にまとめ、識別できる情報だけ残す。URL を捏造しない。

目安は、異なる URL が8本以上である。下回るなら調査の幅が足りない。Haiku 版は `[n]` を123個使いながら、7番号が3文献を割ったものだった。

付録の見出しも見出しである。読者が探しに来る名前を付ける。「効果がなかった先行研究」は述語が判定しているので、「検討した代替説明」と名付け、第一文で判定する。

長さのために消してはいけないものがふたつある。調べて外した枝と、外した理由。次に読む人が同じ枝を掘る。もうひとつは、各主張が乗っている一次資料と出典。疑う読者が辿れなくなる。短くするとは、これを下の層へ移すことであって、消すことではない。本文と一緒に付録まで痩せた原稿は、簡潔なのではなく証拠を失っている。

概要から付録を参照しない。参照は本文から下へだけ。

旧スキルの固定目次のうち、本文に戻すのは概要と背景・歴史だけである。残りは章タイトルにせず、次の場所へ着地させる。落ちた要素は消えたのではなく、置き場所を決めていない。

| 旧スキルの節 | 着地 |
|---|---|
| 概要 | `## 概要`（位置づけを含む） |
| 背景・歴史 | `## 背景・歴史 — <経緯の主張>`。年表の全項目は付録 |
| 核となる概念 / 詳細な仕組み | 番号付きテーマ。見出しは結論を言う |
| 具体例・応用 | テーマの根拠。独立した「事例」章は作らない |
| 重要人物・文献 | 人物が主張そのものならテーマ。それ以外は付録 |
| 最新動向・未解決問題 | 今の議論が主張を動かすならテーマ。外すなら付録に理由を残す |
| 関連トピック | 付録 |
| 参考リンク | `## 付録: 出典一覧` |

## ページの見え方

読みにくさの大半は文体ではなく、**一息の長さと、目印の少なさ**である。

### 一息の長さ

| 単位 | 上限 | 超えたときの直し |
|---|---|---|
| 一文 | 目安120字、150字で切る。平均は55〜95字 | 主語と述語を同時に視野に入れられない。`japanese.md` 2.2 の手順で切る |
| 段落 | 5文または250字 | 話題がふたつ。継ぎ目で割る |
| 小節（`###`） | 1,500字 | 根拠の種類で割るか、テーマがふたつ入っていないか見る |
| 節（`##`） | 1,500字を超えたら `###` を入れる | 小節に割る。割れないならテーマが抽象すぎる |

**この表を全部通しても、読みやすいことの証拠にはならない。** 実測では、初版のレポートは一文100字の上限を完璧に守り（超過ゼロ、平均55字）、それでも読みにくかった。逆に旧スキル版は平均96字・最長191字で上限を大きく破りながら読めていた。上限が防ぐのは暴走だけで、読みやすさは太字と見出しと出典の書き方が決めている。次の節で測る。

上限は概要・背景・歴史・L2 の散文にかける。付録の出典一覧や年表のように行が並ぶだけのものは長くてよい。

### 目印

日本語には大文字も語間の空白もない。斜め読みの手がかりは太字・リンク・数字・記号しかない。

- **太字は構造である。個数の上限は設けない。** 太字にするのは、初出の術語・数値と条件・節末の持ち帰りラベル、の3種のみ。目安は本文1,000字あたり3〜8箇所。0.7箇所まで減らすと、本文が均一な灰色の帯になる（初版の実測値である）。
- **つながりの語を段落の先頭へ。** 「したがって」「一方」「ただし」「例外は」。文中に埋めると斜め読みで見えない。
- **中身に合わせて形を変える。** 比較は表、推論は散文、構造は図。一様なテクスチャは、話が切り替わったことを隠す。
- **遠目テスト。** 文字が潰れるまで縮小する。見出し・段落の空白・表・図・太字が帯になって見えること。真っ黒な長方形は、読む前に離脱される。

## レポートと完了メッセージは別物

レポートは論を運び、単独で成立する。完了メッセージは答えを一文で示し、ファイルを指す。一方を他方の要約にしない。チャットに本文を貼ると、長すぎるメッセージと、直した瞬間にずれる複製ができる。

行動や理解に必要な但し書きは**レポートの中**に書く。完了メッセージが見出しの探し方を伝えるのは構わないが、但し書きの置き場にしてはならない。

このリポジトリでは層が物理的にも分かれる。

| 層 | 置き場所 |
|----|----------|
| L1 | 主 `.mdoc` の `## 概要`、およびユーザーへの完了メッセージ（答えの一文と位置づけの一文） |
| 全体像・歴史 | 同じファイルの `## 全体像` と `## 背景・歴史` |
| L2 | 同じファイルの番号付きテーマの節 |
| L3 | 同じファイルの付録。出典 URL を含む |

## Before / After

### Before 1 — 旧スキルの固定目次（発見順）

```markdown
# ソフトウェアの複雑さ

## 概要
## 背景・歴史
## 核となる概念
### Brooks
### Out of the Tar Pit
### Hickey
## 詳細な仕組み・理論
## 具体例・応用事例
## 重要人物・文献
## 最新動向・未解決問題
## 関連トピック
## 参考リンク
```

九つの節を読み終えてから、読者がテーマの全体像を自分で組み立てることになる。どの節も同じ大きさなので、何が支えで何が辞典なのか分からない。**概要と背景・歴史という枠は正しい。** 外すべきなのは、核概念以降が対象名の見出しのまま並ぶことである。

### Before 2 — このスキルの初版（抽象名詞の見出し3つ）

```markdown
# ソフトウェアの複雑さを定義した議論

<要旨 8〜12文、見出しなし>

## 骨格
## 本質と事故の分割
## 再定義の系譜
## 単純と簡単の軸
## 付録: 一次資料と参考リンク
```

目次からは何も分からない。節がそれぞれ4,000字近くなり、三つの壁になる。出典名が文の主語に来るため、読者は意味のない固有名詞を順に処理させられる。

### Before 3 — このスキルの改訂版（位置づけと経緯が落ちた）

```markdown
# ソフトウェアの複雑さを定義した議論

<見出しなしの要旨 4〜6文。答えと範囲だけ>

## 全体像
<図>

## 1. Brooks の本質と事故 — 言語やツールが消せるのは事故の側だけ
## 2. 事故的複雑さの再定義 — 残る複雑さの大半はまだ事故である
## 3. 単純さと簡単さの区別 — 複雑さは絡み合いである
## 4. 複雑さの定義が衝突する場所 — 同じ語で異なる話をしている
## 5. 三つの定義が生まれた背景 — 技術と問題の変化

## まとめ
## 付録: 出典一覧
```

見出しは結論を言い、図もある。だが概要が「この文書は何の文書か」を言わず、経緯がテーマ5として主張の後ろに来る。目次は読めるが、文書の位置づけと、主張が立つまでの筋がない。

### After

```markdown
# ソフトウェアの複雑さを定義した議論

## 概要
<5〜8文。1文目に Brooks か「銀の弾」。3段落目で位置づけ（何を扱い、何が目的か、なぜ今か）と範囲>

## 全体像
<図 — 問い・軸・分かったこと3・答え・扱わない範囲・調査範囲>
<図の下に、関係とテーマの対応を述べる一文>

## 背景・歴史 — 危機の診断から、複雑さを認知のコストで測る三代へ

## 1. Brooks の本質と事故 — 言語やツールが消せるのは事故の側だけ
### 銀の弾がないという主張
### 事故の側で実際に消えたもの
**ここで分かること:** ...

## 2. Tar Pit の再定義 — 残る複雑さの大半はまだ事故である
## 3. 状態と制御の切り分け — 関数型が引き受けた部分
## 4. Hickey の単純と簡単 — 複雑さは部品の数ではなく編み込みである
## 5. 三つの定義が衝突する場所 — 同じ語で別の話をしている

## まとめ — 三つの定義を使い分けるための5点

## 付録: 出典一覧
## 付録: 計測指標と隣接する語彙
## 付録: 検討した二次文献
```

何も消していない。人物、循環的複雑度、関連トピックは付録か、支える一文の中に移った。変わったのは次である。概要が答えだけでなく位置づけを言うこと、全体像が図になって主張の関係が辺に乗ること、経緯がテーマの前にあること、**見出しが結論を言うこと**、テーマが3つではなく4〜8あること、そして**出典が `[n]` になって文の主語が主題側に戻ったこと**である。旧スキルから残すのは概要と歴史の枠であり、核概念以降の章タイトルではない。
