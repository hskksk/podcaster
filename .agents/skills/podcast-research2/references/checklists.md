# 提出前のチェック

`SKILL.md` ステップ4の直前に走らせる。

初版は40個のテストを課していた。実測すると、**数えられるテストは全部通り、数えられないテストは全部落ちていた**（文字数上限は完璧に守られ、目印の少なさと翻訳調は放置された）。規則を増やすほど、「テストを通る原稿」は書けても「読める原稿」からは遠ざかる。

そこで12個に絞り、**数えられるものは計測スクリプトに移した**。

```bash
python3 .agents/skills/podcast-research2/measure.py content/docs/<slug>/index.mdoc
```

**この出力をそのまま報告する。** 目視で見積もった数字を書かない。実測したところ、Haiku エージェントは7つの指標のうち4つを誤って申告した（太字密度を1.48と報告したが実測3.9、平均文長を135字と報告したが実測43.3字、引用数を58と報告したが実測123、本文字数を15,484字と報告したが実測5,135字）。**数えられるテストは自己採点に耐える、という想定は誤りだった。** スクリプトを走らせる。

残りは判断が要るテストである。**上から順に走らせる。** 上ほど、落ちたときの直しが大きい。

## 14のテスト

### 1. 一文テスト
原稿を見ずに、答えを一文で言えるか。

→ 言えないなら、調査に答えがないか、答えが複数ある。問いに答えるひとつを選ぶ。他は付録へ。

### 2. 目次テスト
**目次だけを上から順に読んで、サーベイの結論が言えるか。** `## 概要` と `## 全体像` はスロット名なので例外。`## 背景・歴史 — …` と番号付きテーマは結論を言う。

→ 言えないなら見出しが弱い。テーマは `## <番号>. <対象> — <主張の断片>` の形に直す。抽象名詞句だけの見出しは落ちる。`structure.md`「L2 本文」を見る。

### 3. 概要テスト
概要だけを渡された読者が、答えと、この文書が何の文書かを言えるか。5〜8文に収まっているか。1文目に、読者が知っている具体名詞があるか。何を扱い、何が目的で、なぜ今読むかが書いてあるか。

→ 落ちる典型は、概要が各節の要約になっている場合、「本稿は三つの主張に整理する」で始まっている場合、答えだけで位置づけがない場合である。答えと位置づけから書き直す。方法（どう調べ、どう整理したか）を位置づけと取り違えない。

### 4. 内部語テスト
本文に「見取り図」「枠組み」「射程」「骨格」「スロット」「L1」「L2」「主張1」が出ていないか。`grep` で数える。

→ 出ていたら書き換える。読者はこのスキルを読んでいない。`japanese.md` 1.9。

### 5. 直訳テスト
`japanese.md` 1.3 の置き換え表を本文にかける。「運ぶ」「稼ぐ」「買う」「持つ」「表面積」「〜が教えてくれる」を検索する。造語した複合語（「品質表面積」「人的キャパシティ」）がないか。

→ 一箇所でも残っていたら直す。第1部の検出手順（元の英語が浮かぶか、辞書どおりの絵が成立するか）を使う。

### 6. 出典テスト
`[n]` 番号引用を使っているか。出典名が文の主語になっている文を数える。「〜は述べる」「〜は書く」「〜は指摘する」で終わる文を数える。

→ 出典名が主語の文が全体の20%を超えたら書き直す。「〜は述べる」型はゼロにする。`prose-style.md` 第4節。

### 7. 計測スクリプト
`measure.py` を走らせ、17指標の未達をゼロにする。太字の密度、一文の平均字数、本文字数、内部語、直訳テストの語、出典名が主題位置の文、見出しの形、付録の URL 数と番号の対応まで、ここで機械的に見る。

→ 未達が出たら、出力に添えた直し方に従う。**太字が3を下回ると灰色の帯になり、8を超えるなら見出しが足りない**（`###` に昇格させる）。`## 概要` と `## 背景・歴史 — …` の有無と順序もここで見る。出力の数字を書き換えない。

このスクリプトが判定できないものだけが、以下のテストである。

### 8. 持ち帰りテスト
どのテーマの節末にも、太字ラベル付きの持ち帰りが一行あるか。末尾に番号付きのまとめの節があるか。

→ 年号や定義で終わる節は書き終わっていない。行動指示で終わらせない。

### 9. 構造テスト
- `## 概要` がある。`## 背景・歴史 — <経緯の主張>` が、全体像のあと・番号付きテーマの前にある
- テーマは4〜8（背景・歴史はテーマ数に含めない）。図の主張ノードは3つ（±1）
- どのテーマも、いずれかの主張ノードに属する。図の下の一文で対応を述べている
- 1,500字を超える `##` 節に `###` が入っている。小節は一節あたり2〜4
- `{% diagram %}` の中身がフェンス付きコードブロックで包まれている（包まないと図が出ない）
- 同じ列を持つものが四つ以上並ぶ箇所が、散文ではなく表になっている
- 旧スキルの要素（核概念・仕組み・具体例・人物・最新動向・関連トピック）が、テーマか付録のどこかに着地している。落ちているなら置き場所を決めて戻す

### 10. 証拠の生存テスト
付録に、外した調査の枝とその理由、各テーマが乗っている出典が残っているか。`## 付録: 出典一覧` が `[n]` の番号順にあるか。

→ 短くする過程で消していたら戻す。本文と一緒に付録まで痩せた原稿は、簡潔なのではなく証拠を失っている。

### 11. 口調テスト
未確認のことが、未確認だと見えるか。一次資料を読んでいない箇所が、文からそう分かるか。提言（誰が・いつまでに）が混ざっていないか。

→ 何を確認し、何をしていないかが文に出るように直す。

### 12. 作例テスト
`references/structure.md` の Before/After と Mermaid の作例から、文字列をそのまま写していないか。ノードの文、見出しの句、`扱わない範囲` や `調査範囲` の中身を照合する。

→ 作例は**型**であって、使い回す句ではない。写していたら、このテーマの内容で書き直す。Haiku エージェントに作例と同じ題材を与えたとき、Mermaid の8ノードすべてが作例と文字単位で一致した。

### 13. 出典テスト
付録の出典が**互いに異なる文献**か。同じ論文の別版・別ページ・別解説を別番号に分けて本数を稼いでいないか。各項目に URL があるか。

→ Haiku 版は `[n]` を123個使いながら、付録の7番号が Brooks・Tar Pit・Hickey の3文献を割ったものだった。`measure.py` の「互いに異なる URL の数」が8未満なら、調査の幅が足りない。

### 14. 遠目テスト
文字が潰れるまで縮小する。見出し・段落の空白・表・図・太字が帯になって見えるか。

→ 真っ黒な長方形なら、段落を割り、つながりの語を先頭へ移し、値の列を表へ移し、節に `###` を入れる。

## 数えられる指標

テスト2〜7は機械的に数えられる。実測値を添える。

`measure.py` の出力がこの表を兼ねる。手で測るのは目次テストだけである。

| 指標 | 目標 | 初版 | 旧スキル | 改訂版 |

| 目次だけで結論が言えるか | 通ること | × | ○ | ○ |
| 出典名が主題位置にある文の割合 | 10%以下 | 25% | 46% | 2% |

計測はどれも**本文だけ**にかける（付録の出典一覧より前、図の中身を除く）。範囲を変えると数字が動くので、比べるときは範囲を揃える。

**本文字数は判定に入れない。** 短いレポートが悪いわけではない。調査が薄いかどうかは、字数ではなく「互いに異なる URL の数」で見る。

**一度外した指標がひとつある。** 当初は「散文の文数 ÷ 本文1,000字」を主要な指標に置き、同じ情報を少ない文で書けているかを測るつもりだった。三本を揃えて測ると、これは**一文の平均字数を裏返しただけ**で、情報の詰まり具合を測っていない。表では平均字数に置き換えてある。

出典名の割合も、最初は「文頭22字以内に英字トークンがあるか」で測っていた。改訂版は「Raw Vault は」「LDTS を」のように技術語で文を始めるので、この測り方では55%に見える。出典名の一覧と突き合わせる検出に変えると3%になる。**指標が目標を外したときは、直す前に測り方を疑う。**

## 自己採点が効かないもの

書き手は、自分の原稿が落ちているテストを通してしまう。

**数えられるテストも自己採点に耐えない。** 当初この節には「数えられるテストは自己採点に耐える」と書いてあったが、実測で否定された。Haiku エージェントは7指標のうち4つを誤って申告し、しかも過大と過小の両方向に外した。だから `measure.py` を置いた。**数字は実行して得る。読んで見積もらない。**

判断が要るテスト（1・2・3・8・9の歴史と着地・11・12・14）は機械化できない。落ちる箇所は、事実を調べれば済むところではなく、判断が要るところに集まる。見出しが結論を言えているか、概要が位置づけを言えているか、経緯がテーマの前にあるか、持ち帰りが書けているか、未確認が未確認に見えるか、作例を写していないか。

これらを自分で通したときは仮とし、通過の根拠にした箇所を引用する。箇所を名指すことが、通ったつもりを捕まえる。

## すでに長すぎる原稿の直し順

並べ替えを先にすると無駄になり、答えを決めずに切ると間違ったものを消す。

1. 答えを一文で書く。以後はすべてこれに対して判定する。
2. それを支える三つの主張を選ぶ。既存の節に印を付ける。主張を支える／支えない。
3. 支えない節を、名前の付いた付録へ移す。まだ消さない。
4. 概要を5〜8文で書き直す。1文目に具体名詞を置く。位置づけ（何を扱い、何が目的か、なぜ今か）と範囲を入れる。
5. 残した節を4〜8のテーマに整理し、**見出しを `## <番号>. <対象> — <主張の断片>` に書き直す**。
6. `## 背景・歴史 — <経緯の主張>` を全体像のあと、テーマの前に置く。年表の全項目は付録へ。
7. 本文の出典名を `[n]` に置き換える。文の主語を主題側に戻す。
8. 各テーマの主張を一行に畳み、三つの主張ノードに割り当てる。図を作り、下の一文で対応を書く。
9. 各テーマの節末に持ち帰りを一行足す。末尾にまとめの節を作る。
10. 太字を3種に整理する。密度を数える。
11. 長さを測る。1,500字超の節に `###` を入れ、250字超の段落を割り、散文になっている一覧を表へ移す。
12. `japanese.md` 1.3 の置き換え表を本文にかける。
13. `measure.py` を走らせ、未達をゼロにする。出力をそのまま報告する。
14. 残りの判断が要るテスト（目次・概要・歴史・持ち帰り・口調・作例・遠目）を見る。
