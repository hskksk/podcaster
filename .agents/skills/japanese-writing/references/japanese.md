# 日本語で書くときの作法

出力言語が日本語のときに読む。**必読**。

このガイドは、読みにくさの原因となる「直訳調（翻訳病）」の解消と、自然で論理的な日本語の作成を目的としている。

内容はミクロからマクロへのレベル順（語彙 → 文構造 → 文の推敲 → 段落・配置）で構成されている。

**優先順位**: 条文が食い違うときは、**保護リスト・1.2「定着した言い回し」・2.2の定着した無生物主語**など、より具体的な「残す／許容」の記述に従う。一般的な「直す」規則とぶつかる場合は、例外・定着の側を優先する。

# 第1章 語彙と表現（ミクロレベル）

## 1.1 語種のバランスと専門用語

語彙の選定では、無理に和語（大和言葉）へ直さず、その分野や文脈で定着している表現を優先する。

### 変換・和語化してはならない定着語（保護リスト）
学術・ビジネス・IT等の専門領域や日常語として定着している用語・カタカナ語は、そのまま維持する。無理に和語化すると定義が曖昧になり、可読性が低下する。

* **ビジネス・ガバナンス用語**: コンプライアンス、アジェンダ、ガバナンス、リスク、コスト、マネジメント、ステークホルダー
* **専門・技術・データ用語**: データ、API、スキーマ、プロセス、モデル、アルゴリズム、インデックス、エビデンス、コミット、デプロイ
* **定着したカタカナ・和製英語**: イメージ、システム、メンバー、プロジェクト、キャパシティ（処理能力・容量の意味）

※専門領域の用語（例: 「コミット」「キャパシティ」等）を一般的な和語に機械的置換するのは不可。

### 和語に直す対象
直すべきなのは専門用語そのものではなく、英語の比喩やビジネス口語表現、および不必要な官公庁調の言い回しである。

```
硬い: 当該手法の継続的運用には相当規模の人的資源投入が要求される。
自然: この手法を運用するには、相当の人数が必要である。
```

| 英語の比喩・口語 | 適切な日本語表現 |
|---|---|
| drive adoption / rollout | 普及を進める / 展開を進める（「ドライブする」単体は不可） |
| buy-in | 合意を得る / 関係者の賛同 |
| leverage X | Xを活用する / Xに載せる（「レバレッジ」単体は不可） |

## 1.2 動詞の置き換えと比喩の処理

英語の文書の言い回しを一語ずつ日本語に置き換えると、文法的には正しいものの、日本語として読んだことのない不自然な文ができる。直す際は、意味を保ったうえで**短い言い換え**を優先する。

### 直すことが多い置換パターン（イメージの崩れ）

辞書的な意味を適用したときに、日本語として比喩のイメージが成立しない表現は置き換える。

| 検出パターン（英語・直訳） | 変換後の自然な表現 |
|---|---|
| X carries Y （XはYを運ぶ） | XがYを表す / 示す / 担う |
| X earns one's keep （Xは稼ぐ） | Xは役に立っている / 価値がある / コストに見合う働きをする |
| earn a pass （通過を稼ぐ） | テストを通る / 合格とみなす / 条件を満たす |
| X buys you Y （XはYを買う） | XでYが得られる / XのおかげでYを省略できる |
| buy back （買い戻す） | （時間を）取り戻す / 挽回する |
| make X honest （Xを正直にする） | 形式だけにせず厳密にする / 欺瞞のない検証にする |
| cosmetic （化粧の） | 見せかけの / 名目だけの / 表面的な |
| wearing the wrong hat （帽子を間違えた） | 役割を間違えた / 置き場所が違う |
| count your breath （一息を数える） | 一息で読める長さに収める / 短く区切る |
| hold only what is true （真であるものだけを持つ） | 正しいデータだけを保持する / 正性の高い情報だけを扱う |
| X tells us （Xは教えてくれる） | 主語を **2.2 の定着カテゴリ**（論文・研究・結果・実験など）に置けば **〜が示す／〜から分かる／〜が教えてくれる** でよい。主語が生ログ・欠測の塊・ファイルなど、擬人化の絵が崩れるものだけ直す |
| the question is open （問いは開かれている） | 未解決である / まだ議論が続いている |
| X is not yet done （Xは尚未完） | Xはまだ終わっていない / まだ完了していない |

### 文脈で決める表現（定着度と長さで判断）

| 検出パターン | 判定・変換指針 |
|---|---|
| surface area （表面積） | 単なる比喩の「表面積」は避ける。「対象範囲」「設置面」「サーフェス」など定着した語を使う。 |
| parallel threads （並行する糸） | 文脈に応じて **並行する議論**・**並行スレッド**・**並行処理** を使用する。 |
| X allows Y （XはYを許す） | **許可する**・**可能にする** が標準。「許す」単体の一人称的表現のみ避ける。 |
| X sees Y （XはYを見る） | 観察・検知では **検出する**・**捉える** を優先。定着した「〜を見る」は残してよい。 |
| X is promising （Xは有望だ） | 「具体的に何に使えるか」を一行で簡潔に書くほうが明確な場合は具体化する。 |
| X knows Y （Xは知っている） | **モデル・エージェント・組織等**が主語なら許容。静的なログ・単なるデータの主語では避ける。 |

### 定着した言い回し（変換せずそのまま使う）
以下の表現は英語起源であっても日本語の文章に定着しているため**変更しない**。無理に言い換えると文が長くなるか、構造の説明が損なわれる。

* **〜を可能にする** — （「〜できるようにする」と同等に許容）
* **〜に寄与する** — （硬いが短い。毎回「役に立つ」に崩さない）
* **〜を実現する** — （「実現の実施」等の名詞化でなければ動詞として広く許容）
* **重要なのは〜である** — （注意喚起の枠組みとして有効。※直後に理由・手順・条件が続くなら残す）
* **本稿は〜を調査する / Nつの論点に整理する** — （冒頭での構造説明として維持）

## 1.3 特殊な動詞「持つ (have)」の扱い

英語の *have / has* を機械的に「持つ」と訳すと不自然な文になる。表現したい真意（文脈）に応じて具体語へ置換する。

```
NG: このレポートは著者を持たない。
OK: 著者名は掲げない。（または「筆者の補足なしで読める」）

NG: 各節は同じ四つの契約を持つ。
OK: どの節も次の四つの条件（契約）に従う。（または「仕様を満たす」）

NG: この戦略は二つの柱を持つ。
OK: この戦略には二つの柱がある。
```

※プログラミングや法務等の領域で定着している表現（「クラスがメソッドを持つ」「契約が効力を有する / 持つ」「役職が権限を持つ」）は修正不要。

## 1.4 名詞化の解体と複合語の整理

### 名詞を動詞に戻す
英語文脈では動詞を名詞化し、汎用動詞（make, perform, achieve）で支える傾向がある。直訳すると「〜の〜を行う」「〜化をもたらす」という重い文になる。日本語では**動詞のまま**書く。

```
NG: レイヤ境界の明確化の実施が、品質事故の重大性の低減をもたらす。
OK: レイヤの境界を明確にすると、品質事故の重大性を抑えられる。
```

* **危険な連鎖パターン**: 「〜化」＋「〜性」＋「〜の実施 / を行う / をもたらす」
* **保護するドメイン名詞**: 定着した術語（「正規化」「冪等性」「可観測性」「ガバナンス」など）は名詞のまま維持する。

### 複合語を勝手に作らない
英語は名詞を並置するだけで複合語を作れるが、日本語では助詞を補うか定着した熟語を使う必要がある。定着していない名詞の連続や、数式が存在しない文脈での比喩的な数学用語（「不等式」「関数」など）の持ち込みは避ける。

```
NG: 品質表面積が増える。
OK: 品質保証の対象が広がる。

NG: 開発複雑性の最適化を行う。
OK: 開発の複雑さを抑えるよう設計を整える。
```

# 第2章 文の構造と主述（メゾレベル）

## 2.1 修飾語の位置と係り先

修飾語と係り先の距離が開くほど、読者の短期記憶に負荷がかかる。

* **原則1: 長い修飾語を前に、短い修飾語を後ろに置く**
  * **OK**: 十年前に読んだ古びた厚い本
  * **NG**: 厚い古びた十年前に読んだ本
* **原則2: 節（〜する）を先に、句（〜の）を後に置く**
  * **OK**: Raw Vault は、監査のために履歴を残す層であり、挿入のみで運用する。
* **原則3: 主語と述語の距離を最短にする**
  * **OK**: Hub と Link を分けるのは、ソースの追加に強くするためであり、この設計が運用コストの大半を決める。

## 2.2 主述の対応とねじれの解消

### 主述のねじれの確認
文脈が長くなると主題（主語）と述語の文法的な対応が崩れる。最小構文（主語＋述語）を取り出して確認する。

```
NG: このアプリの特徴は、誰でも簡単に画像が編集できます。
（検証: 「特徴は」＋「編集できます」 → ねじれ）
OK: このアプリの特徴は、誰でも簡単に画像を編集できることである。

NG: 運用記事の半分は、SQLよりもトレーニング計画と合意形成の失敗談である。
OK: 運用記事の半分では、SQLではなくトレーニング計画と合意形成の失敗が取り上げられている。
```

### 無生物主語の扱いと定着例の容認
日本語の無生物主語は使用できる動詞が英語より限定されるが、**日常用語や各種専門領域で広く定着している「無生物主語＋動詞」はすべて例外として広く許容し、直さず残してよい**。

* **学術・研究**: 「論文が指摘する」「研究が明らかにする」「結果が示す」「実験が証明する」
* **ビジネス・法務・経済**: 「会社が発表する」「法律が規定する」「条文が定める」「市場が反応する」「契約が成立する」
* **日常・自然・生活**: 「薬が効く」「症状が現れる」「台風が接近する」「電車が遅れる」「時計が7時を指す」
* **IT・技術**: 「モデルが理解する」「システムが監視する」「APIが返す」「プログラムが処理する」

直す対象は、**上記リストにない主語**での過剰な擬人化（「生のログが教えてくれる」「ファイルが望んでいる」）や不自然な重い構文のみである。英語の *tells us* を直すときは、主語を論文・研究・結果など定着カテゴリに置き、1.2 の表どおり **示す／から分かる／教えてくれる** を使えばよい（1.2 と矛盾しない）。

## 2.3 主題の立て方（「は」と「が」）

* **「は」**: 既に話題に出ているもの、これから継続して論じる**主題**（Topic）を立てるとき。
* **「が」**: 初めて文脈に導入するもの、文中で新しく特定する**新情報**（Focus）を示すとき。

```
弱い: Raw Vault を BI に直結しない運用が、公開事例で最も一貫して推される。
強い: Raw Vault は BI から直接読ませない。これが公開事例で最も一貫している境界である。
```

# 第3章 文の推敲と表記（マクロレベル・文）

## 3.1 簡潔化と一文一義

### 基本的な執筆習慣
* **一文一義で短く切る**: 長い複文は分割する。ただし、条件と主張が一体となった文であれば無理に分けなくてよい。
* **文体は常体（〜である、〜した、〜ない）で統一する**: 指定がない限り「です・ます」は混在させない。
* **重複の排除**: 一文の中での単語の重複、同じ接続詞（さらに、また）の連打、段落末の無駄な言い換え要約を削除する。
* **二重否定・受身の連続を避ける**: 能動態や明確な肯定表現に変換する。
* **体言止めは表・箇条書きのみ**: 散文では文末を動詞・述語で結ぶ。

### 簡潔化の4段階フロー
1. **一文を一つの主張に絞る**: 条件・主張・例示を独立した文へ分割する。
2. **名詞を動詞に戻す**: 「改善を実現する」→「改善する」。
3. **重複する内容を削る**: 言い換えや無意味な要約を削る。
4. **不必要な修飾語を削る**: 「基本的に」「実際に」「非常に」「〜ということ」などを削除する。

```
長い: この方式を採用することによって、更新処理の実行時における競合の発生を抑制することが可能になる。
短い: この方式なら、更新時の競合を減らせる。

詰め込み: キャッシュは応答を速くするが、無効化が遅れると古い値を返すため、更新頻度が高い画面ではTTLを短くする必要がある。
分ける: キャッシュは応答を速くする。一方、無効化が遅れると古い値を返す。そのため、更新頻度が高い画面では、TTLを短くする必要がある。
```

## 3.2 冗長フレーズ・レトリック・AI構文の削除

中身を伴わないメタ表現や英語的レトリック、およびAIが生成しがちなボカシ構文（ヘッジ表現）は書き換える。

### 空枠の rhetoric と AI 構文の変換表

| 検出される不自然なフレーズ | 何が問題か | 変換ルール（どう直すか） |
|---|---|---|
| 〜に他ならない | 言い切りを曖昧にする装飾 | 削る。結論をそのまま書く。 |
| 〜という観点から（だけ） | 宣言のみで論脈が進まない | 削るか、「〜では」で主題を立てて具体的な論考を書く。 |
| 〜において（重複・冗長） | 二重・三重の「〜において」や不必要な枠組み化 | 削るか「〜では」「〜に関して」へ変換する。 |
| 〜と言えるだろう / 〜と考えられます | 根拠なき責任の先送り・AI構文 | 根拠があるなら**言い切る**（「〜である」）。不明確なら「未検証」「〜までは特定できない」と明記する。 |
| 〜について見ていきましょう / 解説していきます | 進行をメタ説明するクッション句 | **完全に削る**。直接内容から書き始める。 |
| 重要なのは〜（後ろに具体がない） | 抽象語で終わる空枠 | 直後に理由・条件・手順を必ず続ける。続かないなら枠ごと削る。 |

```
NG: 実際の処理の実装において、提案手法における有効性の検討を行う。
OK: 本手法により、処理速度とメモリ消費量がどう改善するかを検証する。

NG: この変更によりパフォーマンスが向上すると考えられます。まずは設定項目について見ていきましょう。
OK: この変更によりパフォーマンスが向上する。設定項目は次の通りである。
```

### 比喩・借り語の変換

```
NG: 読者が持ち帰るものは、検証の手順である。
OK: ここでの結論は、検証前にスキーマとソルトを揃えることだ。

NG: このチェックリストは設計レビューの肩代わりにならない。
OK: チェックリストがあっても、設計レビューは省略できない。
```

### 制作メタを読者向け本文に出さない
執筆・編集プロセス用の用語（「骨格」「スロット」「この節の役割は」「プロンプト」等）を読者向けの本文や見出しに露出させない。

## 3.3 記号と表記ルール（読点・中黒・英数字）

### 読点の打ち方
用途は以下の4つに限定する。
1. **節と句の切れ目に打つ**（構造を示す標準用途）
2. **語順で誤読を防げないときに打つ**（修飾の向きを固定する）
3. **対比・強調のために打つ**
4. **それ以上は打たない**

※まず語順を調整し、読点がなくても一意に読める配置にするのが原則。

### 列挙には中黒（・）を使う
文中で名詞や単語を並列する場合は、読点ではなく中黒（・）を使用する。

```
NG: 列順、NULL処理、ソルトを揃えないと、JOIN が成立しなくなる。
OK: 列順・NULL処理・ソルトを揃えないと、JOIN が成立しなくなる。
```

### 英数字・記号の表記規則
* **固有名詞・コード**: 原文（英語）の表記をそのまま維持する（訳さない）。
* **スペース（分ち書き）**: 和文と英数字の間に**半角スペースを入れない**（例: 「2026年」「Raw Vaultは」）。
* **数字・単位**: 数字および単位は**半角**（100 MB, 24時間）を使用する。
* **括弧**: 中身が和文を含む場合は全角「（）」、英数字のみの場合は半角()を使用する。

# 第4章 段落と視覚的構造化（マクロレベル・文章）

## 4.1 段落間の接続表現

段落間の論理関係に応じて適切に選択する（不要な場合は置かなくてよい）。

| 論理関係 | 使用する接続表現 |
|---|---|
| 順接・帰結 | したがって / そのため / この結果 |
| 逆接・対比 | 一方 / これに対して / ところが |
| 限定・留保 | ただし / とはいえ / この点は |
| 追加・並列 | さらに / 加えて / 同様に |
| 転換 | ここまでは〜だった。次に / 話題を変えると |
| 具体化 | 具体的には / たとえば |
| 言い換え | つまり / 言い換えると |

## 4.2 数値・データの構造化

複数の数値や比較データを散文の中に列挙しない。データ比較は表（テーブル）に切り出す。

```
NG: ハッシュの性能は、MD5 の CHAR(32) で TEMP が最大、RAW(16) で中程度、数値サロゲートで最小となる。

OK:
| 表現形式 | TEMP 使用量 | 処理コスト |
|---|---|---|
| CHAR(32) | 最大 | 高 |
| RAW(16) | 中程度 | 中 |
| 数値サロゲート | 最小 | 低 |
```

## 4.3 太字（ボールド）の適用ルール

太字は装飾ではなく**構造表示**の手段である。**1段落につき最大1〜2箇所まで**とし、以下の3種のみに適用する。

1. **初出の主要な専門用語**
2. **重要な数値および分岐条件**
3. **結論となる最も重要な結果・判定**

長い段落で、初出術語と条件・結論の両方に太字が要る場合は上限を超えてもよい。ただし**太字だらけにしない**——その段落で読者に残したい判断は**2点以内**に絞る。
