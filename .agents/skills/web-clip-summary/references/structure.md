# クリップの骨格

書き始める前に読む。`compression.md` で「何を残すか」を決めたあとの、「どう並べるか」である。

## 0. 作例をそのまま写さない

このファイルの Before/After と骨子表の作例は**型**であって、使い回す句ではない。見出しの句も、表の列名も、対象の記事の内容で書く。同系のスキルで実測したところ、題材が作例に近いと、エージェントは作例の文をそのまま写した。

## 1. 全体の並び

```markdown
# <記事の主張を言うタイトル>

<要旨。見出しなし、3〜5文>

## 骨子
<3〜6行の表>

## 1. <対象の名詞句> — <主張の断片>
## 2. <対象の名詞句> — <主張の断片>
…（節は2〜6）

## この記事を疑うなら   ← 任意
## 出どころ
{% callout type="note" %} クリップ時の補足 {% /callout %}   ← 任意
```

読む順は上からだが、**書く順は「骨子表 → 要旨 → 本文」**である。表に値を並べると、記事の主張が何行で立つかが分かる。それを見てから要旨を書く。

## 2. タイトル

**記事の題を訳すのではなく、記事の主張を言う。** 元の題は出どころに残る。

- 原題: "Why We Moved Off Kubernetes"
- NG: 「なぜ我々は Kubernetes をやめたのか」（題の訳。中身が分からない）
- OK: 「Kubernetes からの撤退 — 3人のチームには運用コストが合わなかった」

一覧画面ではタイトルしか見えない。半年後の自分が、タイトルだけでこのクリップを開くかどうか決められる形にする。

## 3. 要旨（3〜5文）

見出しなしで、`#` の直後に置く。

**1文目に記事の主張そのものを置く。** 「本記事は」「この記事では」「著者は」で始めない。

順序は **主張 → 根拠の型 → 効く範囲** である。書誌情報（著者、媒体、日付）は要旨に入れず、出どころに置く。

### Before / After

Before:

> 本記事では、Kubernetes から撤退した経験について述べられている。著者は小規模チームでの運用負荷を問題視しており、代替として選んだ構成についても触れられている。移行の過程で得られた知見がいくつか紹介されている。

読んでも何も残らない。「述べられている」「触れられている」「紹介されている」の三つが、中身の代わりに置かれている。

After:

> 3人のチームで Kubernetes を1年運用し、開発に使えた時間が週あたり6時間削られていたため、単一 VM と systemd に戻した。撤退の判断は、可用性ではなく**人数**で決まっている。ノード追加の自動化やローリング更新は動いていたが、CRD とオペレータの追従、証明書更新、クラスタ本体のアップグレードが残り続けた。移行後も monorepo のビルドは変えていないため、この記事が答えているのは「デプロイ先の選択」だけである。

固有名（systemd、CRD、オペレータ、monorepo）と数値（3人、1年、週6時間）が残り、**効く範囲**（人数で決まる／答えているのはデプロイ先だけ）まで入っている。

## 4. 骨子の表

3〜6行。列は **主張 / 根拠 / 効く範囲** を基本に、記事に合わせて変えてよい（比較記事なら「対象 / 値 / 条件」、手順記事なら「工程 / やること / つまずく点」）。

**表には値を置き、理由は本文に置く。** 同じ文を表と本文で二度書かない。

| 主張 | 根拠 | 効く範囲 |
|---|---|---|
| 運用負荷は人数で決まる | 3人で週6時間が運用に消えた | チーム10人未満 |
| 止まらなかったのはクラスタではなく周辺 | CRD 追従・証明書更新・アップグレードが恒常作業 | マネージド利用時も同じ |
| 単一 VM で足りた | ピーク 400 req/s、SLO 99.5% | この負荷帯まで |

表が7行を超えるなら、それは骨子ではなく本文である。節に割る。表が2行なら、表にする意味がない。散文にする。

**箇条書きで代用しない。** 「主張と根拠と条件」のように同じ列を持つものが3つ以上並ぶなら表である。箇条書きにすると対応が読めなくなる。

## 5. 節（2〜6）

見出しは `## <番号>. <対象の名詞句> — <主張の断片>` の形にする。

- NG: `## 2. 運用上の課題`（対象だけ。結論がない）
- NG: `## 2. 運用は大変だった`（主張だけ。対象がない）
- OK: `## 2. クラスタ本体の更新 — 四半期ごとに2日が固定で消えた`

**目次テスト**: 目次だけを上から順に読んで、記事の主張が言えるか。言えないなら見出しが弱い。

### 節の中身

- 第一文が、見出しの主張を条件付きで言い直す
- 続く段落が根拠と数値
- 節が1,200字を超えたら `###` で割る
- **節の本体が箇条書きだけ、は禁止**（骨子と出どころは例外）

### 原文の章立てをなぞらない

記事は書き手の都合で並んでいる。導入があり、伏線があり、結論が最後に来る。クリップは**読み返す側の都合**で並べる。結論が先、条件が次、経緯は落とすか末尾に回す。

原文の見出しを訳して並べただけのクリップは、目次テストで落ちる。

## 6. 逐語引用

**3箇所まで、各2文まで。**

引くのは、**著者の言い回しそのものが情報になる文**だけである。事実は要約すればよい。引用が要るのは、断定の強さ、皮肉、条件の言い切り方が、言い換えると消えてしまうときである。

英語は原文のまま引き、直後に訳を置く。

> "We didn't outgrow Kubernetes. We never grew into it."
> （Kubernetes から卒業したのではない。最初から入っていなかった）

引用が4箇所以上あるなら、それは要約ではなく抄訳である。要約に戻す。

## 7. 「この記事を疑うなら」

任意の節。次のどれかがあるときだけ置く。

- 根拠が著者の一環境だけで、一般化に飛びがある
- 著者の立場（所属、製品の販売元）が結論に効いている
- 反例が既知である
- 数値の測定条件が書かれていない

**無ければ節ごと落とす。** 埋めるために難癖をつけない。

## 8. 出どころ

```markdown
## 出どころ
- 元記事: Jane Doe, [Why We Moved Off Kubernetes](https://example.com/post)（example.com、2026-03-12）
- 記事が引いている出典: [Kubernetes CRD ドキュメント](https://kubernetes.io/docs/...)、[SRE Book 第3章](https://sre.google/...)
- 取得日: 2026-09-19
```

- **元記事は必ず URL 付きで書く。** frontmatter の `url` にも同じものを入れる
- **記事が引いている出典は、実体を確かめたものだけ URL を付ける。** 確かめていないなら題だけ書き、「未確認」と添える
- 取得日を書く。記事は書き換わる

## 9. 補足の callout

原文にないことを書く場所。ここ以外には書かない。

```markdown
{% callout type="note" %}
**クリップ時の補足（原文にない）**: 同じ判断を 2024年の記事[別URL]でも見た。こちらは人数ではなくコンプライアンス要件が理由になっている。
{% /callout %}
```

原文の限界を指摘するのは本文に書いてよい（「著者は書き込み負荷に触れていない」）。それは原文の観察であって、外から足した知識ではない。

## 10. 分量

**上限は 8,000字。下限はない。** 目安は下の表だが、**原文にどれだけ水増しがあるかで大きく動く。**

| 原文（日本語） | クリップの目安 |
|---|---|
| 〜3,000字 | 600〜1,000字 |
| 3,000〜8,000字 | 1,000〜2,500字 |
| 8,000〜20,000字 | 2,500〜6,500字 |
| 20,000字〜 | 上限 8,000字 |

**原文が英語なら、この表の原文字数を 2.4 で割ってから引く。** 英語1語はおよそ日本語2.5字になるので、英語 6,000字（約1,000語）の全訳は日本語で約2,500字である。英語記事の要約が原文の 40% の字数になっていても、圧縮できていないことがある。`measure.py` の「全訳比」がこれを出す。

記事によって圧縮できる量は大きく違う。宣伝と言い換えで膨らんだ記事は1割に落ちるが、事実だけを並べたポストモーテムは8割残る。**後者を無理に縮めると事実が落ちる。** 全訳比が90%を超えたときだけ、落とせるものを探し直す。

字数を埋めるために原文にない知識を足さない。

一文は目安120字、150字で切る。段落は5文／250字まで。

## 11. 太字

太字は日本語の唯一の斜め読みの手がかりである。大文字も語間空白もないため、太字を削ると文字の帯になる。

3種類だけに使う。

1. 初出の術語
2. 数値とその条件
3. 持ち帰りのラベル（`**判断の分かれ目:**` など）

1,000字あたり3〜8箇所。**3を下回ると灰色の帯になり、8を超えるなら見出しが足りない**（`###` に昇格させる）。

`****` は太字にならない。`**` を入れ子にしない。Mermaid のノードの中では `**` が効かないので `<b>` を使う。
