# 何を落とし、何を残すか

原文を読み終えた直後、書き始める前に読む。

## 1. 要約が壊れる道筋

要約が使えなくなる原因は、短すぎることではない。短くする**やり方**である。

**根っこは一つで、1.1 が原因、1.2 以降はその症状である。** 順序を取り違えて症状だけ直すと、数字は揃っているのに読めない要約ができる。

### 1.1 骨子の喪失（これが原因）

骨子とは **主張・根拠・効く範囲** の三つである。原文を読み終えた時点でこの三つを一文ずつ書けないなら、要約は始められない。

書けないまま書き始めると、記事が「何を言ったか」ではなく「何に触れたか」を並べることになる。**そこから他の失敗が全部出てくる。** 主張が言えないから上位語でぼかし（1.2）、中身がないから記事の存在を説明し（1.3）、足りない分を自分の知識で埋める（1.4）。

**見分け方**: できたクリップを見ずに、「この記事は何を主張したか」「なぜそう言えるか」「どこまで効くか」を口で言う。言えないなら骨子がない。

**直し方**: 字数をいじらない。原文に戻って三つを書き出し、それから並べ直す。骨子が決まれば、何を落としてよいかは自動的に決まる。

### 1.2 抽象化圧縮

具体を上位語に置き換えて字数を減らす。骨子をつかめていないときに必ず出る。

三段階で見ると位置が分かる。

| 段階 | 書いたもの | 何が足りないか |
|---|---|---|
| NG | 複数のキャッシュ戦略を性能面で比較している | 骨子も具体もない |
| 不足 | p99 は LRU 0.8ms、Redis 3.2ms、Memcached 2.9ms | 具体はあるが、読者が何をすればよいか分からない |
| OK | **ネットワークを越えるだけで p99 が4倍になる**（LRU 0.8ms / Redis 3.2ms）ので、キャッシュは分散させないほうがよい | — |

**具体を戻すだけでは足りない。** 2段目は1段目より情報が多いが、判断には使えない。数値は主張に付いて初めて裏付けになる。

他の例も同じ構造である。

| 原文にあったもの | NG | OK |
|---|---|---|
| Postgres 14 で `REINDEX CONCURRENTLY` が使えるようになった | 新しいバージョンで再インデックスが改善された | **Postgres 14 以降は再インデックスで書き込みを止めなくてよい**（`REINDEX CONCURRENTLY`） |
| 月額 $20 / 100万リクエストまで、超過分は $2 / 10万 | 従量課金制である | **100万リクエストまでは月 $20 で頭打ち**、超過は 10万あたり $2 |

**見分け方**: 要約の一文から、元記事にあった固有名か数値を復元できるか。できないなら抽象化圧縮である。ただし復元できても、その文が何も主張していなければ2段目で止まっている。

**直し方**: まず主張を書く。そのあとに値を括弧で添える。この順で書けば、字数はほとんど増えない。「複数のキャッシュ戦略を性能面で比較している」（22字）と上の OK 例（55字）の差は33字で、そのぶん読者は元記事を開かずに済む。

### 1.3 紹介文化

記事の中身ではなく、記事の存在を説明してしまう。

- 「本記事では、マイクロサービスの分割基準について解説している」
- 「著者の経験にもとづき、いくつかの観点が示されている」
- 「後半では具体的な実装例が紹介されている」

どれも、読んだ人が何も持ち帰れない。**「〜について」「〜が紹介されている」「〜がまとめられている」は、要約の失敗を示す定型句である。** `measure.py` がこの型を数える。

この定型句が出るのは、書いている側が記事の主張を言えていないからである。**定型句だけ言い換えても直らない。** 1.1 に戻る。

**直し方**: 「〜について解説している」を消して、解説の中身を書く。

- NG: 「マイクロサービスの分割基準について解説している」
- OK: 「分割の基準はドメインではなくデプロイ頻度である。週1回と日10回のコードを同じサービスに置くと、遅い側が速い側を止める」

### 1.4 混入

原文にない知識が、原文の主張と同じ口調で混ざる。半年後に読み返したとき、どこまでが記事かが分からなくなる。

要約の価値は「元記事に辿り着ける」ことにある。そこが濁ると、クリップは記憶のメモ以下になる。

**直し方**: 足したいことは `{% callout type="note" %}` の「クリップ時の補足（原文にない）」に入れる。本文には入れない。原文が触れていない論点を、原文の限界として書くのは可（「著者は書き込み負荷に触れていない」）。それは原文の観察であって、追加の知識ではない。

## 2. 残すものと落とすもの

**骨子はこの表に載っていない。** 残すかどうかを選べるものではなく、落ちたら要約が成立しないためである。以下は、骨子が立ったあとに何を裏付けとして連れてくるかの話である。

### 残す（原文の値のまま）

| 種類 | 例 | 理由 |
|---|---|---|
| **数値** | 3.2ms、38万スター、$20/月、72% | 判断に使う。丸めない。単位と測定条件も一緒に残す |
| **固有名** | Redis、Baileys、grammY、`REINDEX CONCURRENTLY` | 検索の取っ手になる |
| **バージョンと日付** | Postgres 14、2026年3月時点 | 賞味期限が分かる |
| **条件と限界** | 「単一リージョンでのみ」「書き込みが1%未満の場合」 | 条件を落とした主張は嘘になる |
| **反証と失敗例** | 著者が試して駄目だった構成 | ここが記事の一番の価値である場合が多い |
| **手順の分岐点** | 「ここで同期か非同期を選ぶ」 | 手順そのものは落としてよいが、選択が生じる箇所は残す |
| **根拠の型** | 実測か、運用経験か、引用か、意見か | 記事の重みが決まる |

### 落とす

| 種類 | 例 |
|---|---|
| **前置きと背景** | 「近年、クラウドの普及にともない…」 |
| **言い換えの繰り返し** | 英語の技術記事は同じ主張を導入・本文・結論で3回言う。1回にする |
| **例示の重複** | 同じことを示す例が3つ並んでいたら、最も具体的な1つ |
| **宣伝・導線** | 製品の売り込み、ニュースレター登録、著者紹介、関連記事リンク |
| **既知の一般論** | 「テストは重要である」「トレードオフがある」 |
| **比喩の展開部** | 比喩の結論だけ残し、たとえ話の筋は落とす |
| **コードの全文** | 差分の要点だけ。5行を超える引用は原則落とす |

### 判断が要るもの

- **コード**: 1〜3行で意味が立つもの（API の呼び方、設定キー）は残す。長い実装は落とし、「実装は元記事にある」と書かない（書かなくても読者は元記事を開ける）
- **表**: 原文の表が3列以上で値が詰まっているなら、列を絞って移す。表を散文に流し込まない
- **図**: 原文の図が主張の骨格そのものなら Mermaid で写す。装飾なら落とす

## 3. 圧縮の手順

**骨子から始める。値の抜き出しから始めない。**

1. 原文を読み終えた時点で、**主張・根拠・効く範囲**を一文ずつ書く。書けないなら読み直す
2. 主張を 2〜6 の節に割る。**原文の章立てには従わない**。この時点で各節の見出しに結論を書く
3. 原文を段落単位で見て、各段落に「値」「主張」「繰り返し」「前置き」のどれかを振る
4. 「繰り返し」「前置き」を全部落とす。ここで原文の3〜5割が消える
5. 「値」を抜き出し、2 で作った節に配る。**どの節にも属さない値は、骨子が足りないか、値が不要かのどちらかである。** 前者なら節を足し、後者なら落とす
6. 節に配りきれない重要な値だけを骨子の表に置く

この順で進めると、節の見出しが先に立つので、値は主張の裏付けとして収まる。**先に値を抜き出すと逆になり、値の一覧に見出しを後付けすることになる。** そうやって書いた要約は数値が揃っていても読めない。

## 4. 著者の主張と、記事が引く事実を分ける

記事には二種類の内容がある。

- **記事が引いてきた事実**: 他の論文・ドキュメント・計測。辿れる
- **著者の主張**: その事実からの解釈。辿れない

この二つを同じ口調で書くと、クリップは著者の意見を事実として保存してしまう。

- NG: 「Raft はリーダー選出に時間がかかるため、大規模クラスタには向かない」
- OK: 「著者の環境では、ノード50台でリーダー選出に平均2.4秒かかった。そこから大規模クラスタには向かないと結論している」

後者は、2.4秒という事実と、向かないという解釈を分けてある。読者は解釈を採らずに事実だけ採れる。

## 5. 翻訳が絡むとき

英語記事を日本語に要約するときは、原文の構文が頭に残ったまま日本語に移りやすい。`japanese.md` 第1部の全部が効くが、要約でとくに出るのは次である。

- 原文の主語をそのまま主語にする。英語は無生物主語を好むが、日本語では述語を動詞に戻す（「この設計はレイテンシの削減をもたらす」→「この設計でレイテンシが下がる」）
- 原文の一文を一文に対応させる。英語の長い一文は、日本語では二文に割る
- 術語を訳しすぎる。定訳がないものは原語のまま使い、初出だけ括弧で補う
