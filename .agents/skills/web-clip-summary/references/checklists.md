# 提出前のチェック

`SKILL.md` ステップ4の直前に走らせる。

数えられるものは全部スクリプトに移してある。

```bash
python3 .agents/skills/web-clip-summary/measure.py content/web-clips/<dir>/index.mdoc --source-chars <原文の字数>
```

**この出力をそのまま報告する。** 目視で見積もった数字を書かない。同系のスキルでの実測で、エージェントは7つの指標のうち4つを誤って申告した（太字密度を1.48と報告したが実測3.9、平均文長を135字と報告したが実測43.3字、引用数を58と報告したが実測123、本文字数を15,484字と報告したが実測5,135字）。**数えられるテストは自己採点に耐える、という想定は誤りである。** スクリプトを走らせる。

そして、**スクリプトが通ることと、良いクリップであることは別である。** 同じ実測で、エージェントは指標をすべて正しく報告したうえで、唯一の未達を「学術的に正当で許容可」と自分で通した。判断が要るところは自分では通せない。下の9テストは目で見る。

## 帯の根拠を残しておく

`measure.py` の「一文の平均字数」は **50〜95** である。元にした `podcast-research2` は 55〜95 だった。クリップでは値を骨子の表に移すため、散文に残る文が短くなる。そのぶん下限を5字下げた。**これは計測ではなく判断である。** 手元にあるのは、下限を割ったときに切れ切れになるという実測（平均43.3字のレポートが読みにくかった）だけで、クリップでの最適な帯はまだ測っていない。

## 指標を通すための捏造は、未達より重い

要約スキル固有の危険がここにある。「数値の密度」と「異なる固有名の数」は、原文にない数字や製品名を書けば簡単に通る。**通してはならない。**

原文に数値がなければ、参考値が低いまま報告し、「原文が一般論にとどまるため」と一行添える。クリップの価値は元記事に辿れることだけで成り立っている。捏造した数字が一つ入れば、そのクリップは全部信用できなくなる。

**この二つは合否に入れていない。** 数字を散らせば通ってしまい、骨子のない要約を止められないためである。参考値が低いときは、値を足すのではなく骨子テストに戻る。

## 11のテスト

**上から順に走らせる。** 上ほど、落ちたときの直しが大きい。

### 1. 骨子テスト

**クリップを見ずに、三つを口で言う。**

1. この記事は何を主張したか
2. なぜそう言えるのか（実測か、運用経験か、引用か、意見か）
3. どこまで効くのか（条件、限界、著者が認めている弱点）

→ 一つでも言えないなら、**ここで止まる。** 字数も具体もいじらない。原文に戻って三つを書き出し、それから並べ直す。骨子が立っていないクリップは、数値が揃っていても読めない。

これが一番上にある理由は、下の失敗がほぼ全部ここから出てくるからである（`compression.md` 1.1）。主張が言えないから上位語でぼかし、中身がないから記事の存在を説明し、足りない分を自分の知識で埋める。

**スクリプトはこれを測れない。** 骨子に効く機械的な指標は「結論を言っている見出し」と「骨子の表」の二つだけで、どちらも形を見ているだけである。

### 2. 代替テスト

**このクリップを読んだあと、元記事を開き直す必要があるか。**

→ 開き直す必要があるなら、落としてはいけない具体が落ちている。`compression.md` 2節の「残す」表と照らす。どの行が抜けたか特定する。

これが一番大事なテストである。字数が短いことは問題ではない。開き直すことが問題である。

### 3. 復元テスト

クリップの各文から、元記事にあった固有名か数値を復元できるか。できない文を数える。

→ できない文が半分を超えたら、抽象化圧縮で書いている（`compression.md` 1.2）。上位語を消して名前と値を戻す。

**復元できても、その文が何も主張していなければ落ちる。** 数値を並べただけの文は、抽象化圧縮より情報は多いが読者の判断には使えない。主張に値を付ける形に直す。

### 4. 抄訳テスト

`measure.py` の「全訳比」を見る。**90%を超えていたら、要約ではなく抄訳になっている。**

→ 落とせるものを探し直す。`compression.md` 2節の「落とす」表と照らし、前置き・言い換え・例示の重複・宣伝がまだ残っていないか見る。

**ただし、原文が事実だけで埋まっている場合は 80% を超えて正常である。** 障害報告、リリースノート、仕様の変更履歴にはそもそも落とすものがない。無理に縮めれば事実が落ちる。**この指標に合否はない。** 90%を超えたときに一度見直す、という使い方をする。

### 5. 目次テスト

**目次だけを上から順に読んで、記事の主張が言えるか。**

→ 言えないなら見出しが弱い。`## <番号>. <対象> — <主張の断片>` の形に直す。原文の見出しを訳しただけの見出しはここで落ちる。

### 6. 要旨テスト

要旨だけを渡された読者が、記事の主張と効く範囲を言えるか。3〜5文に収まっているか。

→ 落ちる典型は、要旨が各節の要約になっている場合と、「本記事は」「この記事では」で始まっている場合である。主張から書き直す。

### 7. 層のテスト

記事が言ったこと / 記事が引いた出典 / クリップ時に足した補足の三つが、読んで区別できるか。

→ 区別できないなら混入している（`compression.md` 1.3）。足したものは `{% callout type="note" %}` に移す。移せない（原文と絡んでいる）なら、その文は消す。

### 8. 主張と事実のテスト

著者の解釈を、事実と同じ口調で書いていないか。

→ 「Raft は大規模クラスタに向かない」と書いてあれば落ちる。「ノード50台で選出に平均2.4秒かかり、そこから向かないと結論している」に直す（`compression.md` 4節）。

### 9. 直訳テスト

`japanese.md` 1.3 の置き換え表を本文にかける。「運ぶ」「稼ぐ」「買う」「持つ」「表面積」「〜が教えてくれる」を検索する。造語した複合語がないか。

→ 一箇所でも残っていたら直す。英語記事の要約では、原文の構文が頭に残って出やすい。第1部の検出手順（元の英語が浮かぶか、辞書どおりの絵が成立するか）を使う。

### 10. 自立テスト

元記事を指す語（「上記の手法」「先述のとおり」「この記事の後半で」）が残っていないか。半年後に、クリップだけ読んで意味が通るか。

→ 残っていたら、指している中身をその場に書く。

### 11. 遠目テスト

画面を引いて、文字の帯になっていないか。太字と表と見出しが、目の止まる場所を作っているか。

→ 灰色の帯なら太字が足りない。うるさいなら太字が多すぎるか、見出しが足りない（`###` に昇格させる）。

## 落ちたときの直し順

**長すぎる**（8,000字超、または全訳比90%超）:

1. 言い換えの繰り返しを削る。同じ主張が二度出ている箇所を探す
2. 例示を1つに絞る
3. 節を統合する。7節あるなら、どれかは他の節の一部である
4. 原文の経緯・時系列の記述を落とす
5. それでも長いなら、記事が二本分の内容を持っている。クリップを二つに分ける

**短すぎて代替テストに落ちる**:

1. 落とした値の一覧（`compression.md` 3節の在庫）を見直す。配り先がなくて落ちた値を骨子表に入れる
2. 条件と限界が入っているか見る。ここが抜けると、短さに関係なく使えない
3. **字数を足すために原文にない知識を書かない。** 足りないのは字数ではなく値である

**具体の密度が足りない**:

1. 原文に値があるか確認する。あるなら戻す
2. 原文にないなら、未達のまま報告する。「原文が一般論にとどまる」と書く
