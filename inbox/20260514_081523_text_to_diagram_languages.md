# Text-to-Diagram 言語の多角的調査レポート：D2, Mermaid, PlantUML を超える世界の可視化

## 概要
「Text-to-Diagram（コードで図を描く）」の世界は、エンジニアの生産性向上やドキュメントの「腐敗」防止において極めて重要な役割を果たしています。Mermaid や PlantUML、近年急速に普及している D2 などのメジャーなツールは広く知られていますが、実はそれ以外にも特定の用途に特化したり、独自の哲学に基づいた「図描画言語」が数多く存在します。

本レポートでは、ユーザーから指定のあった既知のツール（D2, Mermaid, PlantUML, SVG）を除外し、古典的な Graphviz から、学術的な TikZ、ハードウェア設計用の WaveDrom、さらには現代的な AI 統合型 DSL まで、多様な Text-to-Diagram 言語を網羅的に調査・解説します。

---

## 背景・歴史
Text-to-Diagram の歴史は、1970年代から80年代にかけての「UNIX哲学」に基づいたドキュメント作成ツールに遡ります。

1.  **古典期 (1980年代):** Bell 研究所の Brian Kernighan 氏らによって開発された `PIC` や、AT&T 研究所で生まれた `Graphviz (DOT)` がこの分野の祖です。これらは「テキストで構造を記述し、ツールが最適にレイアウトする」という現在の Text-to-Diagram の基本原則を確立しました。
2.  **学術・組版期 (1990-2000年代):** LaTeX の普及に伴い、数式と同等の精度で図を記述したいという需要から `PGF/TikZ` が誕生しました。また、Python の台頭とともに `BlockDiag` シリーズなど、特定の図種に特化したライブラリが登場しました。
3.  **モダン Web 期 (2010年代-現在):** ブラウザ上で動作する JavaScript ライブラリ（Dagre, Mermaid 等）が登場し、Markdown プレビューとの統合が進みました。近年では、GitHub などのプラットフォームがネイティブ対応したことで爆発的に普及しています。
4.  **AI・ハイブリッド期 (2020年代中期-):** AI による自動生成（Diagrams as Code + AI）や、コードの管理性と GUI の微調整機能を両立させたハイブリッド型（Eraser 等）が登場し、エンジニアリング以外の領域にも広がっています。

## 核となる概念と主要言語

### 1. Graphviz (DOT 言語)
Graphviz は「ノードとエッジ」の関係性を記述することに特化した、この分野の生ける伝説です。
- **特徴:** 強力な自動レイアウトエンジン（dot, neato, fdp 等）を複数搭載。
- **強み:** 巨大で複雑なグラフ（依存関係、ネットワーク等）の可視化において、他の追随を許さない配置の美しさを持ちます。

### 2. PGF/TikZ
LaTeX 環境におけるデファクトスタンダードです。
- **特徴:** プログラミング言語に近い柔軟性を持ち、座標、ループ、条件分岐を用いて「完璧な図」を生成できます。
- **強み:** 学術論文レベルの高精細な図、ベクター形式の極致。

### 3. Pikchr (ピクチャー)
SQLite の作者 D. Richard Hipp 氏が、古典的な PIC 言語を現代の Web（SVG）向けに再構築したものです。
- **特徴:** 安全性を重視し、無限ループやメモリ攻撃を排除した設計。
- **強み:** 非常に細かい位置調整が可能で、技術文書内に精密な図を埋め込むのに適しています。

### 4. Structurizr DSL
ソフトウェアアーキテクチャの記述手法「C4モデル」の公式 DSL です。
- **特徴:** 「図を描く」のではなく「モデルを定義する」思想。
- **強み:** 1つの定義（モデル）から、システム全体図、コンテナ図、コンポーネント図など、視点の異なる複数の図を整合性を保ったまま出力できます。

### 5. WaveDrom
デジタル回路のタイミングチャートを記述するための JSON ベースの言語です。
- **特徴:** `1`, `0`, `p` (clock) などの簡潔な記号で波形を表現。
- **強み:** FPGA や ASIC 開発、通信プロトコルの仕様策定において必須級のツールです。

## 詳細な仕組み・理論

### 自動レイアウトアルゴリズム
Text-to-Diagram ツールの心臓部はレイアウトアルゴリズムです。
- **階層型 (Sugiyama-style):** `dot` や `Dagre` (Nomnoml のエンジン) が採用。ノードを階層（Rank）に分け、エッジの交差を最小化するように配置します。
- **力学モデル (Spring-embedder):** `neato` や `fdp` が採用。ノード間に引力と反発力を計算し、物理シミュレーションのように安定した位置を探ります。

### Diagrams as Code (DaC) の哲学
`Diagrams (Python)` のようなツールは、Python のオブジェクトとしてインフラ構成を記述します。
```python
with Diagram("Cloud Architecture"):
    lb >> EC2("worker") >> RDS("db")
```
このアプローチにより、インフラのコード（Terraform 等）と図のコードを同じリポジトリで管理し、CI/CD パイプラインで常に最新の構成図を自動生成することが可能になります。

## 具体例・応用事例

### ケース 1: 大規模マイクロサービスの可視化
Graphviz を用い、数千のマイクロサービス間の依存関係を JSON から DOT へ変換し、自動生成。人間が手で描くのが不可能な規模のシステム全容を一目で把握できます。

### ケース 2: データベース設計と EER 図
`Gleek` を使用。通常の ER 図だけでなく、継承関係（サブクラス/スーパークラス）を含む拡張 ER 図（EER）を爆速でスケッチし、チームでの議論を活性化。

### ケース 3: ASCII アートからのプロフェッショナル SVG 生成
`Svgbob` を活用。README ファイル内にテキストで描かれた「|--[  ]--|」のような ASCII アートを、Web サイト上では美しいベクター曲線として表示。テキストとしての読みやすさと、画像としての見栄えを両立します。

## 最新動向・未解決問題

### AI による「意図」の解釈
`Eraser (DiagramGPT)` や `Whimsical AI` のように、自然言語で「AWS でスケーラブルな Web サイトの構成を描いて」と指示すると、最適なコンポーネントを選択し、DSL を生成する流れが加速しています。

### 統合レンダラーの台頭 (Kroki)
多種多様な DSL が存在することによる「環境構築の煩雑さ」を解決するため、`Kroki` のような統合 API サービスが標準になりつつあります。20種類以上の言語を1つのエンドポイントで画像化できるため、ツール間の切り替えコストが劇的に低下しました。

### 未解決問題：複雑な図の「手動微調整」と「コード管理」の矛盾
「完全に自動レイアウトすると微妙に重なるが、座標を指定するとコードの管理性が落ちる」というジレンマは、依然としてこの分野の大きな課題です。Pikchr や D2 がこの問題に挑戦していますが、決定的な解決策はまだ模索されています。
