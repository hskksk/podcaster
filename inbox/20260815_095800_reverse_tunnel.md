# リバーストンネル：ngrok、Cloudflare Tunnel、Azure Relay を中心とした技術解説

## 概要

リバーストンネル（reverse tunnel）とは、**ファイアウォールやNATの内側にあるサービスを、外向き接続だけでインターネットやクラウドから到達可能にする**ネットワーク技術である。従来の「パブリックIPを取得し、ルーターでポートフォワーディングを設定し、DMZにサーバーを置く」というアプローチを逆転させ、**内側のエージェントが先に外部のリレー（エッジ）へ接続を張る**ことで、インバウンドポートを開けずに双方向通信を実現する。

代表的な製品・サービスとして、開発者向けの **ngrok**、CDN/WAF/Zero Trust と統合された **Cloudflare Tunnel**（`cloudflared`）、エンタープライズのハイブリッドクラウド接続を担う **Azure Relay Hybrid Connections** がある。いずれも「Control Connection（制御用の長寿命接続）」と「Proxy/Data Connection（実際のトラフィック用接続）」を分離する共通アーキテクチャを持つが、ターゲット、セキュリティモデル、運用思想は大きく異なる。

なぜこの技術が重要か。第一に、**NAT/CGNAT（キャリアグレードNAT）の普及**により、家庭用回線やモバイル回線ではインバウンド接続が原理的に不可能なケースが増えている。第二に、**Webhook開発・ローカルデモ・IoTデバイス管理・オンプレミス連携**など、「一時的または限定的に内部サービスを外部から触りたい」需要が爆発的に増えた。第三に、**Zero Trust（ゼロトラスト）** の潮流の中で、「ネットワーク境界＝信頼」という前提が崩れ、**アイデンティティとポリシーで保護された接続経路**としてリバーストンネルが再評価されている。

一方で、リバーストンネルは**攻撃者にも使われる**。ngrok、frp、SSHリバーストンネルはランサムウェアやAPTグループ（ToddyCat等）によるC2（Command & Control）や持続的バックドア構築に悪用される事例が報告されており、CISOの間では「開発者の便利ツール」と「セキュリティリスク」の間で緊張関係が続いている。

## 背景・歴史

### SSHリバーストンネル：原点

リバーストンネルの概念は、SSH の `-R` オプション（リモートポートフォワーディング）にまで遡る。2000年代から、NAT背後のサーバーが「外向きSSH接続を張り、リモート側のポートをローカルへ転送する」パターンが広く使われてきた。

```bash
# NAT内のマシンから実行：リモートVPSの9000番をローカル22番へ転送
ssh -nNTR 9000:localhost:22 user@remote-vps

# VPS上からNAT内マシンへSSH
ssh -p 9000 local-user@localhost
```

この方式の特徴は、**追加ソフトウェア不要**（SSHさえあればよい）、**VPS等の中継サーバーを自分で管理できる**点である。欠点は、接続の永続化（`autossh` が必要）、HTTP/HTTPS向けのホスト名ルーティングやTLS証明書管理、マルチプレクシングの非効率などである。`GatewayPorts yes` を `sshd_config` に設定しないと、リモート側のループバックからしか接続できない制約もある。

### Localtunnel：「localhostを公開する」発想の先駆者

2010年1月、Jeff Lindsay（progrium）が **Localtunnel** の最初のプロトタイプを公開した。Twistedで書かれた初期版はHTTPマルチプレクシングがうまく動かず、数ヶ月後に **OpenSSH をラップする方式（v1）** に切り替えた。2011年頃から本格運用され、多くの開発者が「localhostを一時的に公開する」という発想に触れた。

2011〜2013年に v2 として Python/gevent による全面書き直しが行われたが、最終的に Localtunnel は ngrok にマインドシェアを奪われ、現在の `progrium/localtunnel` リポジトリはアーカイブ状態である。ただし、Localtunnel が確立した **Control Connection + Proxy Connection** というプロトコル設計は、後続の ngrok、frp 等に強い影響を与えた。

Localtunnel v2 の PROTOCOL.md には、以下のような明確な記述がある：

- **Control Connection**：トンネルセッションの確立・ハートビート・プロキシ接続数の指示
- **Proxy Connection**：実際のTCPトラフィックを中継する接続のプール

外部クライアントが Frontend に接続すると、Backend がプールから Proxy Connection を取り出し、Client 側にローカルサービスへの接続を指示し、Frontend と Proxy Connection をジョインする。

### ngrok：Go製の開発者インフラへ

2013年3月20日、Alan Shreve（inconshreveable）が Go 言語の学習プロジェクトとして ngrok v1 のプロトタイプを GitHub に公開した。Localtunnel が既に存在していたが、Alan は「Goを学ぶ」「Web開発を楽にする」という動機で独自実装に踏み切った。ngrok v1 は2013〜2016年に活発に開発され、**Control Connection 上の JSON メッセージ**（ReqTunnel、NewTunnel、ReqProxy、RegProxy、StartProxy 等）による制御と、Public Connection ↔ Proxy Connection ↔ Private Connection の3段バイトコピーという設計が特徴だった。

2016年以降、ngrok v2 が開発され、v1 リポジトリはアーカイブされた。v2 はモジュラー設計・有料SaaSとしてスケールし、2023年には5000万ドルのシリーズAを調達、500万ユーザー規模に成長した。ngrok は today「Unified ingress for developers」として、トンネルだけでなく Traffic Policy、OAuth、Webhook 検査、Kubernetes Operator 等を含むプラットフォームへ拡張している。

### Cloudflare Tunnel：Argo Tunnel から Zero Trust 基盤へ

Cloudflare Tunnel（旧称 Argo Tunnel）は、2018年頃の Cloudflare Argo 製品群の一部として登場し、2020年頃から `cloudflared` デーモンによる本格運用が広まった。2021年頃には ngrok と「アーキテクチャ上のいとこ」として認識されるようになり、Cloudflare One / Zero Trust スイートの中核コンポーネントとなった。

Cloudflare の強みは、**DNS・CDN・WAF・DDoS防御・Access（認証）・Load Balancing** との統合である。トンネル自体は無料枠が厚く、永続的な本番公開に適している。

### Azure Relay：BizTalk Services から Hybrid Connections へ

Azure Relay は Azure Service Bus プラットフォームの機能の一つで、もともと **WCF（Windows Communication Foundation）Relay** として .NET/Windows 中心のプロプライエタリプロトコルで提供されていた。2016年頃、**Hybrid Connections** として HTTP/WebSocket ベースのオープンプロトコル版がパブリックプレビューされ、クロスプラットフォーム対応が進んだ。

Hybrid Connections は BizTalk Services の同名機能を置き換えるものであり、WCF Relay と **同一ゲートウェイを共有しつつ別実装** として共存している。Azure App Service の Hybrid Connections 機能、IoT シナリオ、オンプレミス DB/API へのクラウドからのアクセスなど、エンタープライズのハイブリッドクラウド接続で広く使われる。

### frp 等のセルフホスト型

2015年頃から、中国のオープンソースコミュニティを中心に **frp（Fast Reverse Proxy）** が開発された。`frps`（サーバー）と `frpc`（クライアント）の2バイナリ構成で、ngrok のセルフホスト版として世界中で使われている。v2 では K8s/ServiceMesh 的な拡張可能コアを目指す設計に進化している。

## 核となる概念

### 接続方向の逆転（Outbound-Only Model）

従来のサーバー公開：

```
インターネット → [FW/NAT] → サーバー（インバウンド待受）
```

リバーストンネル：

```
サーバー（エージェント）→ [FW/NAT] → エッジ/リレー ← インターネット
                              ↑
                    外向き接続のみ許可
```

ファイアウォールは通常、**アウトバウンド（外向き）通信をデフォルトで許可**する。エージェントが `443` 番（HTTPS）や `7844` 番（Cloudflare Tunnel）へ接続すれば、インバウンドルールを変更せずにトンネルが確立できる。

### Control Plane と Data Plane の分離

ほぼすべてのリバーストンネル実装が、以下の2層構造を持つ：

| 層 | 役割 | 寿命 | 例 |
|---|---|---|---|
| Control Connection | 認証、トンネル登録、ハートビート、新規プロキシ接続の指示 | 長寿命（永続） | ngrok の Control Connection、frp の Control、cloudflared の Control Stream |
| Data/Proxy Connection | 実際のHTTP/TCPトラフィックの中継 | 短命（リクエストごと、またはプール再利用） | ngrok の Proxy Connection、frp の Work Connection |

この分離により、**1本の制御接続で多数の同時リクエストをマルチプレクス**でき、新規外部接続ごとにエージェントが新しいプロキシ接続を張る方式（ngrok の ReqProxy パターン）も可能になる。

### レンデブーポイント（Rendezvous Point）

Azure Relay のドキュメントが明示するように、リバーストンネルは **クラウド上の「待ち合わせ地点（rendezvous point）」** を介して2者を接続する。Listener（内側）と Sender（外側）が同じ Hybrid Connection 名で Azure Relay に接続し、Relay が両者の WebSocket を橋渡しする。

ngrok/Cloudflare Tunnel では、この役割を **グローバル分散エッジ** が担う。DNS でエッジに向け、エッジがトンネル経由でオリジンへ転送する。

### NAT/CGNAT との関係

- **NAT（Network Address Translation）**：家庭用ルーターがプライベートIPを共有グローバルIPに変換。ポートフォワーディング設定があればインバウンド可能。
- **CGNAT（Carrier-Grade NAT）**：ISPがさらに上位でNATを行い、加入者に **100.64.0.0/10** 等のプライベートアドレスしか割り当てない。加入者側のポートフォワーディングは **完全に無意味** になる。

リバーストンネルは CGNAT 環境でも動作する。内側から外向きに接続を開始するため、キャリアのNATを「突破」するのではなく、**そもそもインバウンドを必要としない** 設計だからである。

## 詳細な仕組み・理論

### ngrok のプロトコルとリクエストフロー

ngrok v1 の DEVELOPMENT.md に詳細なフローが記載されている（v2 も概念は同型）：

1. **クライアント（エージェント）** がサーバー（ngrok cloud）へ長寿命 TCP 接続を確立 → **Control Connection**
2. クライアントが `ReqTunnel` メッセージでトンネル作成を要求
3. サーバーが `NewTunnel` で公開URL（サブドメイン等）を返す
4. 外部から **Public Connection** が到着（HTTP Host ヘッダまたは TCP ポートでトンネルを特定）
5. サーバーが Control Connection 経由で `ReqProxy` を送信
6. クライアントが新しい **Proxy Connection** を張り、`RegProxy` で関連付け
7. サーバーが `StartProxy` でメタデータ（クライアントIP等）を通知
8. Public ↔ Proxy、Proxy ↔ Private（localhost:port）の **バイトコピー** が双方向に行われる
9. **Ping/Pong** による死活監視。切断時はクライアントが再接続

HTTP トンネルの場合、TLS で Control Connection 全体が暗号化され、複数の同時 HTTP リクエストが効率的に多重化される。TCP トンネルでは生のバイトストリームが流れる。

ngrok v2 以降の差分：
- Traffic Policy（認証、レート制限、ヘッダ操作）
- Agent Endpoints、Kubernetes Operator
- カスタムドメイン、OAuth/OIDC 連携
- Web インスペクター（localhost:4040）による HTTP リクエストの検査・リプレイ

### Cloudflare Tunnel（cloudflared）のアーキテクチャ

`cloudflared` は Go 製デーモンで、以下のコンポーネントから構成される：

**Supervisor**：最大4本（デフォルト、`--ha-connections` で変更可）の **HA（High Availability）接続** を管理。各接続は異なる PoP（Point of Presence）のエッジIPをターゲットにする。最初の1接続が成功するまで他は起動しない（bootstrap constraint）。

**EdgeTunnelServer**：単一接続のライフサイクルを管理。DNS SRV レコードによる **Edge Discovery** で接続先 IP を解決する。

**ProtocolSelector**：
- **QUIC**（UDP、post-quantum 暗号化、優先）
- **HTTP/2**（TCP、QUIC がブロックされた場合のフォールバック）

QUIC が `IdleTimeoutError` や `operation not permitted` で失敗すると、自動的に HTTP/2 へフォールバックする。

**Orchestrator**：ランタイム設定（ingress rules）を管理し、オリジンプロキシを提供する。

**接続フロー**：
1. `cloudflared tunnel create` で Tunnel UUID を作成、認証情報（credentials JSON）を取得
2. `cloudflared tunnel run` でエッジへ4本のアウトバウンド接続（2データセンター以上）
3. DNS CNAME（`*.cfargotunnel.com` 等）でホスト名をトンネルにマッピング
4. 外部リクエスト → Cloudflare エッジ（CDN/WAF/DDoS）→ トンネル → `cloudflared` → `http://localhost:8080` 等

**ingress 設定例**（config.yml）：

```yaml
tunnel: <TUNNEL-UUID>
credentials-file: /path/to/<TUNNEL-UUID>.json
ingress:
  - hostname: app.example.com
    service: http://localhost:8080
  - hostname: ssh.example.com
    service: ssh://localhost:22
  - service: http_status:404
```

**レプリカ**：同一トンネルに複数の `cloudflared` インスタンスを配置可能（最大25レプリカ＝100接続）。地理的に近いレプリカへトラフィックがルーティングされる。

**ファイアウォール要件**：ポート `7844`（TCP/UDP）への **アウトバウンドのみ**。インバウンドはすべてブロック可能。

### Azure Relay Hybrid Connections のプロトコル

Hybrid Connections は **HTTP と WebSocket** 上に構築されたオープンプロトコルである。

**Listener（オンプレミス側）**：
- Hybrid Connection Manager（HCM）または SDK を使用
- `wss://<namespace>.servicebus.windows.net/$hc/<path>/?sb-hc-action=...&sb-hc-id=...` へ WebSocket 接続
- SAS（Shared Access Signature）または Azure AD トークンで認証
- 接続を維持し、Sender からの要求を待つ

**Sender（クラウド側）**：
- 同じ Hybrid Connection エンドポイントへ HTTP または WebSocket で接続
- `sb-hc-action=listen`（Listener）と異なる action（例：`connect`）で接続
- Relay が両者の WebSocket を **透過的に橋渡し**

**特徴**：
- **プロトコル非依存**：TCP ベースであれば何でも（HTTP、SSH、DB プロトコル等）
- **双方向・ストリーム通信**：WebSocket のバイナリストリーム
- **スコープが狭い**：VPN とは異なり、**単一アプリケーションエンドポイント（ホスト:ポート）** に限定。ネットワーク全体の統合ではない

**WCF Relay との比較**：

| 項目 | WCF Relay | Hybrid Connections |
|---|---|---|
| プロトコル | プロプライエタリ（net.tcp ベース） | HTTP/WebSocket（オープン） |
| .NET Core | × | ○ |
| Node.js/Java | × | ○ |
| 用途 | レガシー WCF アプリ | 新規クロスプラットフォーム |

### frp の Control/Work 分離

frp は ngrok v1 と同型の **Control Connection + Work Connection** モデルを採用：

- **Control Connection**：1クライアント1本、認証・ハートビート・プロキシ登録
- **Work Connection**：プール（`poolCount`）で事前確立、ユーザートラフィック専用

Work Connection プールが空になると `ReqWorkConn` で追加要求。Transport は TCP/KCP/QUIC/WebSocket から選択可能。

**P2P モード（XTCP）**：NAT ホールパンチングで Relay を介さず直接接続を試みる（失敗時はフォールバック）。

**VirtualNet**：TUN インターフェースによる IP レベルルーティング（単純ポート転送を超えたネットワーク接続）。

### Tailscale Funnel：WireGuard メッシュ上のリバーストンネル

Tailscale Funnel は、既存の **WireGuard ベースの Tailscale メッシュ** をトランスポートとして利用する。

1. `tailscale funnel 3000` でノードが Funnel を有効化
2. パブリック DNS（`*.ts.net`）が地理的に近い **Funnel Ingress ノード** を指す
3. 外部ユーザーの TLS 接続（SNI 必須）が Ingress に到着
4. Ingress が **peerapi**（Tailscale ノード間 RPC、WireGuard 復号後に netstack で処理）経由で対象ノードに TCP 接続オファーを送信
5. ノード上の `tailscaled` が TLS を **終端**（Let's Encrypt 証明書を自動取得）し、localhost:3000 へリバースプロキシ

重要な設計判断：**Tailscale は TLS 終端をしない**。Certificate Transparency ログで確認できるように、Funnel 用証明書はノード側で取得・終端する。これにより、Tailscale インフラは暗号化された TCP を中継するだけで、ペイロードを復号しない。

## 具体例・応用事例

### 1. Webhook 開発（ngrok の定番ユースケース）

Stripe、GitHub、Slack 等の Webhook は、インターネットから到達可能な HTTPS URL を要求する。開発者は：

```bash
ngrok http 3000
# → https://abc123.ngrok-free.app → localhost:3000
```

ngrok の Web インスペクター（`http://localhost:4040`）でリクエスト/レスポンスを検査・リプレイできる。これが ngrok の最大の差別化要因の一つ。

### 2. 自宅サーバーの永続公開（Cloudflare Tunnel）

自宅 NAS や Nextcloud をポート開放なしで公開：

```bash
cloudflared tunnel create myhome
cloudflared tunnel route dns myhome nas.example.com
cloudflared tunnel run myhome
```

Cloudflare Access で Google/GitHub 認証を要求すれば、Zero Trust 的な公開が可能。DDoS/WAF も Cloudflare エッジで処理される。

### 3. Azure Functions からオンプレミス SQL Server へ

1. Azure Relay 名前空間を作成
2. Hybrid Connection を `sqlserver.local:1433` で定義
3. オンプレミスに Hybrid Connection Manager をインストール・登録
4. Azure Function の接続文字列で Relay 経由の接続を使用

Function はインターネットに公開されず、DB もインバウンドポートを開けない。

### 4. IoT デバイスのリモート管理（Azure Relay サンプル）

Azure-Samples/secure-tunneling-azure-relay では：

1. デバイスが Azure Relay Bridge で Hybrid Connection を Listen
2. クラウドの Azure Container Instance が同じ Hybrid Connection に Connect
3. ACI がパブリックエンドポイントを公開
4. ユーザーは ACI の FQDN 経由でデバイス上の Web サーバー（port 8080）にアクセス

### 5. CGNAT 下のホームラボ（frp + VPS）

ISP が CGNAT の場合：

```ini
# frpc.ini（自宅）
[common]
server_addr = vps.example.com
server_port = 7000

[web]
type = http
local_port = 80
custom_domains = home.example.com
```

VPS 上の `frps` が公開 URL を提供。Cloudflare Tunnel と組み合わせ、VPS をエッジとして使う構成も一般的。

### 6. エンタープライズ開発者の「Tunnel 禁止と代替」

2025〜2026年、CrowdStrike 等の脅威情報により、企業 SOC が ngrok/VS Code Remote Tunnels をブロックする動きが加速。DevSecOps チームは **Cloudflare Tunnel + Access**、**Tailscale Funnel**、**Teleport** 等、IdP 連携・監査ログ付きの代替を提供する方向へ移行している。

## 最新動向・未解決問題

### セキュリティ：攻撃者による悪用

ToddyCat APT グループは、侵害システム上で **SSH リバーストンネル**、**ngrok**、**frp** を組み合わせた多層トンネルを構築する事例が報告されている。外向き SSH（443番偽装等）がファイアウォールで検知されにくいことが exploited される。

CISO 向けの推奨：
- エンドポイントで ngrok 等のバイナリをブロック
- 許可する場合は IdP 連携・JIT（Just-In-Time）アクセス・セッションログ必須
- 「Tunnel hopping」（localhost.run、serveo 等への迂回）を監視

### Zero Trust との統合

Cloudflare Tunnel + Access、ngrok Traffic Policy + OAuth、Tailscale Funnel + ACL が、**「トンネル＝認証済み経路」** として成熟している。未解決点は、**非人間アイデンティティ（NHI）**——CI/CD エージェント、MCP サーバー、IoT デバイス——がトンネルを張る場合のガバナンス。97% の NHI が過剰権限を持つという調査（NHI Mgmt Group）があり、トンネル＋過剰権限 NHI の組み合わせは特に危険。

### Post-Quantum 暗号

Cloudflare Tunnel は **post-quantum encrypted connections** を標榜。ngrok も TLS 1.3 ベース。長期的には、トンネルプロトコル全体の PQ 対応が競争点になる。

### MCP（Model Context Protocol）とリバーストンネル

2025年、AI エージェントがローカル MCP サーバーを外部から触れるようにするためにリバーストンネルが使われる事例が増加。MCP ツールアクセスは事実上の特権アクセスであり、トンネル経由での外部公開は OWASP Agentic AI Top 10 のリスク領域と重なる。

### プロトコル進化

- **QUIC/HTTP3** ベースのトンネル（cloudflared、frp v2）が主流に
- **WebTransport** 的な低遅延ストリームの採用可能性
- **eBPF** によるトンネルトラフィックの可視化（観測性）

## 関連トピック

### SSH ポートフォワーディング（`-L` / `-R` / `-D`）

| オプション | 方向 | 用途 |
|---|---|---|
| `-L` | ローカル → リモート | ローカルポートでリモートサービスにアクセス |
| `-R` | リモート → ローカル | **リバーストンネル**（NAT突破） |
| `-D` | SOCKS プロキシ | 動的ポート転送 |

### VPN vs リバーストンネル

| 項目 | VPN（WireGuard/IPsec） | リバーストンネル |
|---|---|---|
| スコープ | ネットワーク全体 | 特定サービス/ポート |
| 侵入性 | ルーティング変更 | アプリ層のみ |
| NAT 突破 | 双方向接続が必要な場合あり | アウトバウンドのみで可 |
| 代表例 | Tailscale, Headscale | ngrok, cloudflared |

Tailscale は両方の性質を持つ：メッシュ VPN としての Tailscale と、Funnel によるリバーストンネル。

### インライン（フォワード）トンネル vs リバーストンネル

- **フォワードトンネル**：クライアント → サーバー方向の接続（SSH `-L`）
- **リバーストンネル**：サーバー → クライアント方向の接続（SSH `-R`、ngrok 等）

「reverse」の意味は、**TCP 接続の initiator が内側** という点にある。

### その他の製品

- **Teleport**：SSH/K8s/DB 向け Zero Trust アクセス。リバーストンネル的エージェント。
- **Pinggy**：SSH ベースの簡易リバーストンネル SaaS。
- **inlets**：Kubernetes 向けリバーストンネル。
- **rathole**：Rust 製の軽量リバーストンネル。
- **VS Code Remote Tunnels**：開発環境リモートアクセス（企業ブロック対象になりつつある）。
- **zrok**：オープンソースの sharing プラットフォーム（OpenZiti ベース）。

## 製品比較まとめ

| 観点 | ngrok | Cloudflare Tunnel | Azure Relay HC |
|---|---|---|---|
| 主用途 | 開発・Webhook・デモ | 本番公開・Zero Trust | エンタープライズハイブリッド |
| エージェント | ngrok agent | cloudflared | HCM / SDK |
| 接続先 | ngrok global edge | Cloudflare edge | Azure Relay 名前空間 |
| プロトコル | 独自（TLS+JSON） | QUIC/HTTP2 | HTTP/WebSocket |
| 公開URL | ngrok ドメイン or カスタム | 自ドメイン（CF DNS） | Relay 名前空間 |
| 認証 | Traffic Policy/OAuth（有料） | Cloudflare Access | SAS / Azure AD |
| コスト | 無料枠制限、$8〜/月〜 | 基本無料 | Azure 従量課金 |
| セルフホスト | ×（v1のみOSS） | × | × |
| 観測性 | Web Inspector（強み） | CF Analytics | Azure Monitor |

**選び方の指針**：
- **Webhook 開発・即席デモ** → ngrok
- **自ドメインで永続公開・WAF/DDoS** → Cloudflare Tunnel
- **Azure からオンプレへ安全接続** → Azure Relay Hybrid Connections
- **完全自己管理・コスト最小** → frp + VPS
- **VPN メッシュ＋限定公開** → Tailscale Funnel
