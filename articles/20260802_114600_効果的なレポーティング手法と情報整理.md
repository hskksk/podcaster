# 情報が頭に入ってくるレポートの書き方——コンサル流の整理・まとめ・伝達の技術

## 概要

リサーチレポートや調査報告書を読んでも「情報は豊富なのに頭に残らない」——この違和感は、情報量そのものより**提示の仕方**に原因があることが多い。問題は「過多」と「散乱」の二つが同時に起きているケースが典型で、量が多いうえに論点が並列に散らばり、読者のワーキングメモリを一度に使い果たしてしまう。

経営コンサルティングファーム（McKinsey、BCG、Bain など）が数十年かけて体系化してきたレポーティング手法は、本質的に**認知科学と意思決定の実務**の融合である。Barbara Minto が McKinsey で開発したピラミッド原則、MECE、SCQA といったフレームワークは、情報を減らすためではなく、**読み手の頭の中に「骨格」を先に置いてから肉付けする**ための技術だ。

本レポートでは、なぜ情報が入ってこないのかを認知負荷の観点から分析し、コンサルが実際に使う整理の考え方（Issue Tree、仮説駆動）、伝達の型（結論先出し、Action Title、段階的開示）、日本語ビジネス文脈での適用（PREP 法、ボトムアップ文化との折り合い）、そして AI エージェントが生成するリサーチレポートに特有の構造的欠陥とその対策までを体系的に整理する。

## 背景・歴史

### コンサル流コミュニケーションの誕生

1960年代、McKinsey に入社した Barbara Minto は、複雑なクライアント課題を短時間で伝える必要から、論理構造を可視化する方法論を開発した。1960年代末には MECE（Mutually Exclusive, Collectively Exhaustive：相互に排他的で、全体として網羅的）という概念を生み、1970年代にはピラミッド原則として形式化。1987年に『The Minto Pyramid Principle』として出版され、以降 McKinsey・BCG・Bain を含む戦略コンサル業界の標準言語となった。

同時代、アメリカ軍では BLUF（Bottom Line Up Front：結論を最前線に）という通信規範が確立されていた。生命に関わる判断を迅速に下すため、「結論→根拠→詳細」の順序が義務付けられた。この考え方はビジネス界にも浸透し、Amazon の Jeff Bezos が 2004年に PowerPoint を禁止して six-page narrative memo を導入した背景にも、同じ「断片化された情報より、一貫した論証」を重視する思想がある。

### 認知科学との接続

1956年、George Miller は「The Magical Number Seven, Plus or Minus Two」で、短期記憶が同時に保持できる情報単位（チャンク）がおおよそ7±2個であることを示した。重要なのは、情報量そのものではなく**チャンクの意味的まとまり**だ。電信の点と線を覚える初心者と、単語として覚える熟練者では、同じ記憶容量でも保持できる情報量が桁違いになる。

1980年代以降、John Sweller らの認知負荷理論（Cognitive Load Theory）は、学習・理解のボトルネックを三種類に分類した。

- **内在的負荷（Intrinsic Load）**：題材そのものの複雑さ
- **外在的負荷（Extraneous Load）**：提示方法が生む無駄な負荷（散乱の主因）
- **関連的負荷（Germane Load）**：スキーマ構築に向けた有効な思考負荷

Allan Paivio の二重符号化理論（Dual Coding Theory）も、言語チャネルと視覚チャネルを組み合わせることで記憶定着が向上することを示した。レポート設計においては、テキストだけでなく**構造図・Issue Tree・ピラミッド図**が「第二の符号」として機能する。

## 核となる概念

### 1. ピラミッド原則（Pyramid Principle）

ピラミッド原則の核心は「**考える順序と伝える順序を逆にする**」ことだ。

- **考える（ボトムアップ）**：データ → 分析 → 洞察 → 結論
- **伝える（トップダウン）**：結論（Governance Thought）→ 支持論点（2〜4個）→ 根拠・データ

Minto の定式化では、各階層の論点は下位の論点の**要約**でなければならない。つまり見出しだけ読んでも全体の論証が追える状態が理想だ。

```
                    ┌─────────────────┐
                    │  結論・提言      │  ← 最初に読ませる
                    └────────┬────────┘
              ┌──────────────┼──────────────┐
              ▼              ▼              ▼
         支持論点1       支持論点2       支持論点3   ← MECE
              │              │              │
         データ・根拠   データ・根拠   データ・根拠  ← 詳細は後
```

### 2. SCQA / SCR——読者を「聞く姿勢」にする導入

ピラミッドの「頂点」をいきなり提示しても、読者が「なぜ今それを聞く必要があるのか」を感じなければ離脱する。SCQA は導入部の型である。

| 要素 | 役割 | 例 |
|------|------|-----|
| **S**ituation（状況） | 全員が同意できる現状 | 「当社の顧客離反率は業界平均を上回っている」 |
| **C**omplication（ complication） | 変化・問題・緊急性 | 「新規獲得コストが2倍になったにもかかわらず改善しない」 |
| **Q**uestion（問い） | 解くべき問い | 「どのセグメントで離反を止めるべきか？」 |
| **A**nswer（答え） | 結論・提言 | 「エンタープライズ顧客向けオンボーディングを再設計すべき」 |

プレゼンテーションでは Question を省略した **SCR**（Situation-Complication-Resolution）も使われる。Complication が問いを暗示するため、口頭形式では冗長さを避けられる。

### 3. MECE——整理の「完全性テスト」

MECE は分類の品質基準であり、レポートの章立て・論点・推奨事項のグルーピングすべてに適用される。

- **Mutually Exclusive（相互排他）**：同じ内容が複数の章に重複しない
- **Collectively Exhaustive（全体網羅）**：重要な論点の取りこぼしがない

MECE 違反の典型例：「コスト削減」と「プロセス改善」を別論点にしたが、プロセス改善の大半がコスト削減に直結している（重複）。逆に「技術的要因」と「人的要因」だけに分け、規制変更の影響をどこにも書いていない（漏れ）。

Minto 自身は MECE の発明者として「Mee-cee（1音節）」と発音すると述べているが、McKinsey 内部では「Mee-see（2音節）」が一般的だ。

### 4. BLUF と PREP——段落レベルの結論先出し

**BLUF**（Bottom Line Up Front）は軍事通信から来た原則で、最初の文で Who/What/Where/When/Why を答える。

**PREP 法**は日本のビジネス現場で広く使われる段落構成だ。

1. **P**oint（結論）
2. **R**eason（理由）
3. **E**xample（具体例・データ）
4. **P**oint（結論の再提示）

ピラミッド原則が文書全体の骨格なら、PREP は各セクション・各段落のミニピラミッドである。長いリサーチレポートでも、**各見出しの直下に PREP の P を置く**だけで拾い読み耐性が劇的に上がる。

### 5. What / So What / Now What——意味と行動の橋渡し

1970年 Terry Borton が教育分野で提唱し、Stanford GSB などでも推奨される三層構造。

- **What**：客観的事実・観察
- **So What**：その意味・影響・なぜ重要か
- **Now What**：次に取るべき行動

多くのリサーチレポートは What（事実の羅列）で終わり、So What（意味づけ）と Now What（行動）が欠落している。これが「読んだのに何も残らない」最大の原因の一つだ。

### 6. 水平ロジックと垂直ロジック——論証の2軸

Minto は論証を**水平**と**垂直**の2方向で検証するよう求める。

**垂直ロジック（Vertical Logic）**：「なぜそう言えるのか（Why So?）」——上位の主張を下位の根拠が支持する。ピラミッドの上下関係。

**水平ロジック（Horizontal Logic）**：「だから何（So What?）」——同じ階層の論点同士が、inductive（事例の集積→一般化）、deductive（一般原理→個別結論）、または chronological（時系列）のいずれかでつながる。

多くの散乱レポートは垂直ロジックが弱い（見出しと本文が対応しない）か、水平ロジックが混在している（同じ階層に因果関係のない論点が並ぶ）。執筆後のレビューでは、各段落に「Why So?」と「So What?」を問いかけると構造の穴が見つかる。

### 7. Action Title——見出しを「結論の一文」にする

McKinsey/BCG のスライド文化で確立された Action Title は、見出しをトピック名ではなく**完全な結論文**にする技法だ。

| トピック型（悪い例） | Action Title（良い例） |
|---------------------|------------------------|
| 市場動向分析 | 国内 SaaS 市場は年率18%成長、エンタープライズセグメントが牽引 |
| 競合調査結果 | 主要3社すべてが AI 機能を2025年内に GA 済み |
| コスト構造 | 固定費比率65%が利益率改善の最大ボトルネック |

Action Title だけを順に読んで論証が通るか——これを「**Titles Test（タイトルテスト）**」と呼ぶ。15語以内、能動態、可能なら数値を含める。

## 詳細な仕組み・理論

### 認知負荷の観点：過多と散乱の診断

AI エージェントのリサーチレポートが「頭に入らない」と感じるとき、問題はしばしば以下の組み合わせだ。

| 症状 | 原因 | 対応する技法 |
|------|------|-------------|
| 読むのが疲れる | 外在的負荷が高い（冗長、重複、無関係な詳細） | 付録への退避、1セクション1メッセージ |
| 何が言いたいかわからない | 結論が末尾・見出しがトピック型 | BLUF、Action Title、エグゼクティブサマリー |
| 論点がバラバラ | MECE 違反、Issue Tree 不在 | 章立ての再設計、重複統合 |
| 記憶に残らない | チャンク化不足、So What 欠落 | 3論点に絞る、What-So What-Now What |
| 深掘りしたいのに辿れない | 段階的開示の設計ミス | 3層構造（要約→論証→付録） |

ワーキングメモリの容量は限られる。Cowan (2001) のレビューでは同時保持可能なチャンクは4前後とされる。つまり**支持論点は3±1個**が実務的上限であり、McKinsey が「2〜4個の支持論点」を推奨するのはこの認知制約に沿っている。

### Issue Tree——書く前の「思考の骨格」

優れたレポートは書き始める前に、Issue Tree（論点ツリー）で問題を分解している。

```
                    [なぜ顧客離反率が高いか？]
                              │
            ┌─────────────────┼─────────────────┐
            ▼                 ▼                 ▼
      [製品の問題]      [価格の問題]      [サポートの問題]
            │                 │                 │
      ┌─────┴─────┐     ┌─────┴─────┐     ┌─────┴─────┐
      ▼           ▼     ▼           ▼     ▼           ▼
   機能不足   UX問題  競合より高い  値感不足  応答遅延  品質問題
```

Issue Tree の原則：

1. **トップダウン**：ルートの問いから始める
2. **MECE**：各レベルの枝が重複なく漏れなく
3. **仮説駆動**：最も可能性の高い枝から検証し、「全枝を均等に調査しない」（boiling the ocean を避ける）
4. **テスト可能**：葉のノードはデータで Yes/No を判定できる粒度まで分解

Issue Tree は最終レポートの目次そのものになる。逆に目次が Issue Tree になっていないレポートは、調査の過程で論点が増殖し、散乱した典型例だ。

### 段階的開示（Progressive Disclosure）——情報量と理解の両立

Nielsen Norman Group が提唱する Progressive Disclosure は、UX 設計の概念だがレポート設計にそのまま適用できる。

**3層モデル**：

| 層 | 内容 | 読者の時間 |
|----|------|-----------|
| **第1層** | エグゼクティブサマリー（結論＋3論点＋Ask） | 1〜5分 |
| **第2層** | 各論点の論証（Action Title 見出し＋PREP 段落） | 15〜30分 |
| **第3層** | 付録（生データ、方法論、詳細分析、参考文献） | 必要な人だけ |

重要なのは、第1層だけで**意思決定可能**であること。Stanford GSB の Matt Abrahams も、構造化された情報は処理・記憶されやすいと指摘する。第1層が「概要」ではなく「本体」である——これがエグゼクティブサマリーの本質だ。

### エグゼクティブサマリーの設計

効果的なエグゼクティブサマリーは以下を満たす。

1. **Standalone Test**：本文を読まなくても判断できる
2. **Recommendation First**：最初の文が提言
3. **3つの理由**：支持論点は最大3つ（ワーキングメモリ制約）
4. **Quantified**：可能な限り数値で示す
5. **Named Owner + Date**：誰がいつまでに何をするか
6. **Risk Acknowledgment**：主要リスクを1〜2行で正直に述べる
7. **No Cross-Reference**：「第3章参照」は禁止——必要な情報はサマリー内に要約

Board Paper 向けの **CQC フレームワーク**（Context-Question-Conclusion）も有用だ。Context で状況、Question で決裁者が答えるべき問い、Conclusion で明確な推奨と必要な承認事項を述べる。

### データストーリーテリング——Nancy Duarte の三幕構成

Nancy Duarte（『DataStory』著者）は、データレポートにも物語構造を適用する。

- **第1幕（Setup）**：現状と stakes（何が危うい/チャンスは何か）
- **第2幕（Confrontation）**：データが示す複雑さ・矛盾・トレードオフ
- **第3幕（Resolution）**：データに裏付けられた推奨と期待成果

Duarte の **DataPOV**（Data Point of View）は1文で「データが示す問題＋取るべき行動＋取らない場合のリスク」を述べる。例：「競合3社が AI 機能を GA 済みのため、2026年Q2までに自社も GA しないとエンタープライズ案件の30%を失うリスクがある」。

三幕構成は SCQA と親和性が高い。SCQA が「導入の物語」なら、三幕構成は「レポート全体の物語」だ。

### Amazon 6-Pager——ナラティブの力

Jeff Bezos が PowerPoint を禁止した理由は明確だ。「スライドはアイデアを平坦化し、相対的重要度をぼかし、つながりを無視する許可を与える」。six-page narrative memo は：

- 最大6ページの散文（付録は無制限だが必読ではない）
- 会議冒頭20〜30分の黙読時間
- 結論から始まるが、**論証の流れは散文として一貫**
- 書くこと自体が思考の精緻化

AI リサーチレポートに応用すると、「箇条書きの羅列」ではなく、各セクションを段落として書き、セクション間の接続詞で論理関係を明示する——これだけで理解度が変わる。

### フレームワーク対応表——どの場面で何を使うか

| 場面 | 推奨フレームワーク | 目的 |
|------|-------------------|------|
| レポート全体の骨格 | ピラミッド原則 + MECE | 結論→3論点→根拠 |
| 冒頭1ページ | SCQA / エグゼクティブサマリー | 読む理由 + 判断材料 |
| 各セクション見出し | Action Title | 拾い読み耐性 |
| 各段落 | PREP / BLUF | 段落内の結論先行 |
| 調査設計（執筆前） | Issue Tree + 仮説駆動 | 散乱防止 |
| 情報量の多い本 | Progressive Disclosure | 3層構造 |
| データ中心の報告 | Duarte 三幕 + DataPOV | 意味と行動の接続 |
| 振り返り・報告 | What-So What-Now What | 意味づけと Next Step |
| 散文形式の提案 | Amazon 6-Pager | 論証の一貫性 |

これらは排他的ではない。典型構成は「SCQA で導入 → ピラミッド頂点を提示 → MECE な3論点を Action Title 見出し + PREP 段落で展開 → 各論点末尾に So What → 最後に Now What → 詳細は付録」という**多層の重ね合わせ**だ。

### コンサルタントの執筆プロセス——「書く前に9割決める」

McKinsey Way（Ethan Rasiel）が描く実務プロセスは次の通り。

1. **問題定義**：「何を解くか」を1文で固定（Issue Tree のルート）
2. **仮説形成**：最も可能性の高い答えを先に仮定
3. **分析計画**：仮説を検証するのに必要なデータだけリスト
4. **Storyline 作成**：Word 文書で Action Title のみを並べる（Titles Test）
5. **エグゼクティブサマリー執筆**：Storyline 完成後に書く
6. **本文執筆**：各 Action Title の下に PREP
7. **Appendix 整理**：本編から参照される詳細を移動
8. **MECE 監査**：重複統合、漏れ追加
9. **Standalone Test**：サマリーだけ渡して判断できるか確認

AI リサーチの弱点は、ステップ4（Storyline）とステップ5（サマリー先行）を飛ばして、ステップ7（情報収集）から始めることだ。情報は豊富でも**論証の設計図がない**ため、頭に入らない。

## 具体例・応用事例

### ケース1：散乱した AI リサーチレポートの再構成

**Before（典型的な AI 生成レポート）**：

```
# テーマXについて

## 概要
（500字の背景説明）

## 歴史
（年表型の羅列）

## 主要概念A
（詳細な説明）

## 主要概念B
...

## 最新動向
...

## 参考リンク
（50件）
```

**After（コンサル流再構成）**：

```
# テーマX：【結論】Y を採用すべき——3つの理由

## エグゼクティブサマリー（1ページ）
- 提言：Y アプローチを2026年Q3までに導入
- 理由1：コスト40%削減（根拠：事例A, B）
- 理由2：競合5社中4社が移行済み
- 理由3：規制対応が2027年義務化
- 次のステップ：PoC 90日、担当：〇〇、予算：△△

## 論点1：Y はコスト面で優位である
（PREP 段落 + データ）

## 論点2：市場は既に Y に移行している
...

## 論点3：規制環境が Y を事実上必須にする
...

## 付録A：概念の詳細解説
## 付録B：年表・歴史
## 付録C：参考文献
```

変化のポイント：

- タイトル自体が Action Title
- 歴史・概念の詳細は付録へ（Progressive Disclosure）
- 本文は MECE な3論点のみ
- 各論点が PREP 構造

### ケース2：McKinsey 最終提案書の標準構成

MBB（McKinsey/BCG/Bain）の最終提案はおおむね以下。

1. **Executive Summary（1スライド/1ページ）**：Governance Thought + 3〜5 bullet（各 bullet は完全な claim 文）
2. **Main Body（3〜5セクション）**：各セクション = 1支持論点。セクション冒頭が結論
3. **Recommendations & Roadmap**：Owner、Timeline、Success Metric
4. **Appendix**：感度分析、詳細データ、方法論

BCG は Management Summary を2カラム（左：Findings、右：Recommendations）にする形式も使う。いずれも**本編は argument に必要な最小限、詳細は付録**という Progressive Disclosure の徹底だ。

### ケース3：日本企業への適用——ボトムアップ文化との折り合い

日本のビジネス文書は「背景→経緯→分析→結論」のボトムアップが伝統的だ。突然結論から始めると「根拠がない」と受け取られるリスクがある。

実務的な折り合い方：

1. **エグゼクティブサマリーだけ結論先出し**：本文は従来型でも、冒頭1ページで結論を提示
2. **SCQA で「読む理由」を先に作る**：Situation/Complication で共感を得てから Answer
3. **各章見出しを Action Title 化**：章の中身は背景から入っても、見出しで結論を先に見せる
4. **PREP を段落単位で適用**：章内の読み順は柔軟にしつつ、各論点は結論先行

「全体はトップダウン、段落内は必要に応じてボトムアップ」——これが日本語環境での現実解だ。

### ケース4：「過多」と「散乱」の見分け方

同じ「頭に入らない」でも、対処法は異なる。

**過多（Overload）の兆候**：
- 同じ概念の説明が複数箇所に現れる
- 1セクションに5つ以上のサブトピック
- 参考リンクが本文より長い
- 読了時間の見積もりが想定の3倍以上

**対処**：削る、統合する、付録へ移す。Minto の言葉で「argument に必要なものだけを示す（show exactly what's needed to make the case）」。

**散乱（Scattered）の兆候**：
- 目次の並びに論理関係がない（アルファベット順、調査順）
- 見出しがすべてトピック名
- 結論がどこにあるかわからない
- セクション間の接続詞がない

**対処**：Issue Tree で再構成、Action Title 化、ピラミッド再設計。情報量は同じでも構造を変える。

多くの AI リサーチレポートは**両方**を併発する。情報を集めるたびに新しい見出しが増え（過多）、調査順に並ぶため論理関係がない（散乱）。

### ケース5：ポッドキャスト台本への変換——視覚構造の喪失

本レポートの最終用途がポッドキャスト台本生成である点は重要だ。Issue Tree や表は音声では伝わらない。口頭向けには：

1. **冒頭30秒フック**：SCQA の Complication + Answer（「今日話すのは、〇〇すべきという結論です。理由は3つ」）
2. **3つの論点を明示**：「第一に…第二に…第三に…」
3. **各論点で PREP**：結論→理由→例→結論
4. **So What を声に出す**：「これが意味するのは…」
5. **Now What で締める**：「だから次に…」

視覚的な Action Title は、口頭では**言い切りの一文**に変換する。表や図は比喩か具体例に置き換える。

## 最新動向・未解決問題

### AI リサーチレポート生成の構造的課題

2025〜2026年の Deep Research 系 AI システム（WebWeaver、ScaffoldAgent、CogGen 等）の研究は、AI 生成レポートの問題を明確に指摘している。

1. **Search-then-Generate 問題**：情報を全部集めてから一気に書くと、構造なき冗長な出力になる
2. **Static Outline 問題**：執筆前に固定した目次が、調査の進行と乖離する（scaffold drift）
3. **Loss in the Middle**：長いコンテキストに全部入れると、中間部分の情報が活用されない
4. **Scaffold Drift**：情報が蓄積されるほど、当初の構成との整合性が崩れる

これらは人間のリサーチレポート作成でも同型の失敗だ。AI 研究コミュニティが提案する解は、コンサル手法と驚くほど一致する。

- **Dynamic Outline**：Issue Tree を調査と共に更新（Expansion / Contraction / Revision）
- **Memory Bank + Section-wise Writing**：付録に詳細を置き、セクション単位で執筆
- **Utility-guided Structure**：各セクションが「全体の論証にどう貢献するか」で評価

### 未解決の緊張関係

- **網羅性 vs 簡潔性**：リサーチの価値は「調べた量」に見えるが、読者の価値は「判断できる速さ」
- **学術的厳密さ vs 実務的明快さ**：引用と方法論の詳細は付録へ
- **文化差**：BLUF は一部文化で「攻撃的」と受け取られる——SCQA で cushioning する
- **音声メディア（ポッドキャスト）**：視覚的構造（Issue Tree、表）が使えない——口頭用の要約設計が別途必要

## 実践チェックリスト——「頭に入るレポート」の10項目

レポート完成前に以下を確認する。

1. **One-Sentence Test**：このレポートの結論を1文で言えるか？
2. **Standalone Summary**：エグゼクティブサマリーだけで判断できるか？
3. **Titles Test**：見出しだけ読んで論証が通るか？
4. **MECE Check**：章・論点に重複や漏れはないか？
5. **Rule of Three**：支持論点は3±1個に収まっているか？
6. **So What Check**：各セクションに「だから何？」の答えがあるか？
7. **Now What Check**：推奨アクションに Owner と Date があるか？
8. **Appendix Test**：本編から20%以上削って付録に移せるか？
9. **PREP per Section**：各セクションの最初の文は結論か？
10. **Cognitive Load Audit**：読者が同時に追う概念は4個以下か？

### 事実・解釈・提言の三層分離

優れたコンサルレポートは、以下を明確に区別する。

| 層 | 内容 | 文体 |
|----|------|------|
| **Fact（事実）** | 観測可能、検証可能 | 「2025年Q4の離反率は12%だった」 |
| **Interpretation（解釈）** | 事実から導く意味 | 「これは業界平均の2倍であり、改善余地が大きい」 |
| **Recommendation（提言）** | 取るべき行動 | 「オンボーディングを90日以内に再設計すべき」 |

AI リサーチレポートは Fact の羅列で Interpretation が薄く、Recommendation が存在しないことが多い。Fact だけでは記憶に残らない——**Interpretation（So What）が記憶のフック**になる。

### 推奨事項の4要素

実行可能な提言には次の4要素が必要だ（Sembly AI、McKinsey 系文献より）。

1. **What**：何をするか
2. **Who**：誰が担当するか
3. **When**：いつまでに
4. **Success Metric**：成功の定義

「検討する」「改善を図る」は提言ではない。**Tomorrow Test**——「明日承認されたら、誰が何を始めるか具体的にわかるか」——で検証する。

## AI リサーチレポート向け——具体的改善ガイド

AI エージェントが生成するリサーチレポートを改善する場合、プロンプトや後処理で以下を指定する。

### 生成前（構造の設計）

```
1. まず Issue Tree を出力（MECE、3〜5枝）
2. 仮説を1文で述べる
3. 支持論点を3つに絞る
4. エグゼクティブサマリーの草稿を先に書く
5. 詳細調査は各論点に紐づけて実施
```

### 生成後（構造の修正）

```
1. 全見出しを Action Title（結論文）に変換
2. 「概要」「背景」が長すぎたら付録へ移動
3. 重複セクションを統合（MECE 違反の修正）
4. 各セクション末尾に So What / Now What を追加
5. 参考リンクは付録に集約、本編にはインライン引用のみ
```

### 目標文字数の配分（2万字レポートの例）

| 部分 | 割合 | 役割 |
|------|------|------|
| エグゼクティブサマリー | 5% | 結論・3論点・Ask |
| 論点1〜3 | 各15% | PREP + 根拠 |
| 導入（SCQA） | 5% | 読む理由 |
| 推奨・Next Steps | 10% | Now What |
| 付録 | 30% | 詳細・歴史・参考文献 |

## まとめ——情報は「減らす」のではなく「階層化する」

AI エージェントのリサーチレポートが頭に入らないとき、問題は情報の豊富さそのものではない。多くの場合、**外在的認知負荷**——提示方法が生む無駄な混乱——が原因だ。過多（同じ情報の繰り返し、不要な詳細の本編混入）と散乱（Issue Tree 不在、トピック型見出し、結論の欠落）が重なり、読者のワーキングメモリを空にする。

コンサルタントが数十年かけて磨いた答えはシンプルだ。

1. **書く前に構造を決める**（Issue Tree、仮説、Storyline）
2. **結論を最初に置く**（ピラミッド頂点、BLUF、エグゼクティブサマリー）
3. **論点を3つに絞る**（MECE、Rule of Three）
4. **見出しを結論文にする**（Action Title、Titles Test）
5. **詳細は段階的に開示する**（Progressive Disclosure、付録）
6. **意味と行動を明示する**（So What、Now What、4要素の提言）

情報量を削る必要はない。同じ情報を**ピラミッドの階層**に再配置すれば、読者は第1層だけで判断し、必要なときだけ第2層・第3層に降りられる。これが「豊富でも頭に入るレポート」の正体である。
