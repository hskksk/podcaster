# Jujutsu（jj）：Gitの次を狙う次世代バージョン管理システム

## 概要

Jujutsu（コマンド名 `jj`）は、Google のエンジニアである Martin von Zweigbergk が開発した Git 互換のバージョン管理システム（VCS）だ。2019 年にホビープロジェクトとして始まり、現在は彼のフルタイムプロジェクトとなっている。2024 年には GitHub の Stars が 28,000 を超え、2026 年 4 月時点で v0.40.0 がリリースされるなど、急速に注目を集めている。

Jujutsu が革新的なのは、Git のデータモデルをそのまま使いながらも、「どうしてこんなに使いにくいのか」と長年感じられてきた Git のユーザーインターフェイスを根本から設計し直した点にある。ステージングエリアの廃止、ワーキングコピーのコミット化、ファーストクラスのコンフリクト処理、全操作の取り消し機能——これらの特徴が組み合わさることで、ソフトウェア開発のワークフローを大きく変えうるポテンシャルを持つ。

---

## 背景・歴史

### 開発の動機

Martin von Zweigbergk は Mercurial の元メンテナーであり、Google の内部バージョン管理システム「Piper」の開発にも関わってきた。彼は長年、Git 利用者がリベースやアメンドのたびにコミットハッシュが変わることと戦い続ける様子を目の当たりにし、Mercurial の `evolve` 拡張が一部の問題を解決しながらも古いしがらみを持ち続けていることを知っていた。

2019 年、「バージョン管理を一から作り直すとしたら」という問いのもと、Jujutsu の開発がスタートする。

### 転機

2022 年 5 月、プロジェクトに Git バックエンドが追加された。これにより、既存の `.git` ディレクトリの上に `jj` を重ねて使えるようになり、チームメンバーに移行を強要することなく個人的に使い始めることが可能になった。この「既存 Git リポジトリとの共存」機能が、Jujutsu の普及を大きく後押しした。

### 開発体制

現在は Google 内のいくつかのチームで実際に使われており、事実上の「Google 内部 VCS の後継候補」としての立ち位置にある。2024 年 12 月にはリポジトリが `jj-vcs` GitHub organization に移動し、プロジェクトとして本格的な体制が整いつつある。

## 核となる概念

### 1. ワーキングコピーはコミットである

Git との最大の違いがこれだ。

Git では「編集中のファイル」「ステージされたファイル」「コミット済みのファイル」という三段階の状態が存在し、`git add` によってステージングエリアを経由してコミットを作る。これが初心者の混乱を招き、「ハンクごとのステージング」などの複雑な操作が必要になる原因だった。

Jujutsu ではこの概念がない。**ファイルを編集した瞬間、その変更は自動的に「現在のワーキングコピーコミット」に記録される**。常に何らかのコミットに乗っている状態であり、`jj add` というコマンドは存在しない。

```
# Git でのワークフロー
vim foo.py
git add foo.py
git commit -m "add feature"

# Jujutsu でのワークフロー
vim foo.py
jj describe -m "add feature"   # コミットメッセージをつけるだけ
jj new                          # 新しい空のコミットへ進む
```

### 2. Change ID と Commit ID の区別

Git ではコミットを SHA-1 ハッシュで識別するが、これはコミットの内容に基づいて計算されるため、リベースやアメンドをするたびに変わってしまう。これが「あのコミットはどこへ行った」という混乱の元凶だった。

Jujutsu には二種類の識別子がある：

- **Change ID（変更 ID）**：コミットが誕生した瞬間に生成され、内容を書き換えても変わらない不変の ID。英字のみで構成され（16 進数と混同しないよう意図的に数字を除外）、`kpqxlopt` のような形式をとる。
- **Commit ID（コミット ID）**：コンテンツベースの Git ハッシュ。内容が変わるたびに更新される。

この区別により、「あの変更はリベース後どこにある？」という問いに Change ID で明確に答えられる。

### 3. 匿名ブランチとブックマーク

Git ではすべての開発ラインに名前付きブランチが必要だが、Jujutsu では**匿名ブランチ**がデフォルトだ。コミットは名前がなくても宙に浮いている状態で保持される。

GitHub などへプッシュする際には **ブックマーク（bookmark）** を使う。これは Git のブランチに相当するが、重要な違いがある：Jujutsu には「現在のブックマーク」という概念がなく、新しいコミットを作っても自動的にはブックマークが追従しない。意図的に `jj bookmark set NAME` で更新する必要がある。この設計は「意図しないブランチの前進」を防ぐための意識的な選択だ。

### 4. ファーストクラスのコンフリクト

Git でマージコンフリクトが発生すると、多くのコマンドが使えなくなり、作業が一時停止する。Jujutsu ではコンフリクトは**コミットとして保存**できる。

コンフリクトが発生しても、そのまま別の作業に切り替えたり、コンフリクト状態のコミットの上に新しいコミットを積んだりできる。`jj log` や `jj status` はコンフリクトがあることを教えてくれるが、作業は止まらない。後で `jj resolve` でコンフリクトを解消できる。

### 5. オペレーションログ（操作履歴）

`jj op log` で**すべての操作の履歴**を確認できる。コミット、フェッチ、プッシュ、リベース——あらゆる操作が記録される。

```bash
jj op log          # 操作履歴を表示
jj undo            # 直前の操作を取り消し
jj op restore <ID> # 任意の時点に復元
jj redo            # 取り消した操作をやり直し
```

Git の `reflog` が「コミットの移動履歴」を記録するのに対し、Jujutsu のオペレーションログは「リポジトリに対するすべての操作」を記録する。これにより、「間違って rebase した」「誤って push した」といったあらゆるミスを安全に取り消せる。

## 詳細な仕組み・理論

### 自動リベース

コミット A を修正すると、その子孫コミット（B, C, D...）は**自動的にリベース**される。Git で `git rebase --update-refs` と `git rerere` を組み合わせた挙動が透過的に行われる。

コンフリクトの解消も伝播する。祖先コミットのコンフリクトを解消すると、同じコンフリクトを抱えていた子孫コミットにもその解消が自動的に適用される。

### Revset 言語

`jj log` などのコマンドで使える専用の**クエリ言語**が用意されている（Mercurial の revset から着想を得た）。

```bash
# 基本的なシンボル
@                       # 現在のワーキングコピーコミット
@-                      # 親コミット
main                    # mainブックマーク

# 関数
parents(X)              # Xの親
children(X)             # Xの子
ancestors(X)            # Xの全祖先
descendants(X)          # Xの全子孫
author("名前")           # 特定の作者のコミット
conflicts()             # コンフリクトを持つコミット
files("src/foo.rs")     # 特定ファイルを変更したコミット

# 演算子
X & Y                   # XかつY（積集合）
X | Y                   # XまたはY（和集合）
X ~ Y                   # XのうちYでないもの（差集合）
X::Y                    # XからYまでの範囲
```

### Rust による実装とバックエンド抽象化

Jujutsu は Rust で実装されており、コアライブラリ `jj-lib` とコマンドラインツール `jj-cli` から構成される。ストレージ層は `Backend` トレイトで抽象化されており、現在は Git バックエンド（`GitBackend`）が本番利用可能なほぼ唯一の実装だ。Git バックエンドは `gitoxide` ライブラリを使って Git リポジトリを読み書きする。

Change ID などの Jujutsu 固有のメタデータは `.jj/repo/store/extra/` 以下の `StackedTable` 形式で保存される。これは Git の GC によって消去されないよう設計されている。

## 具体例・応用事例

### 基本的なワークフロー

```bash
# 既存Gitリポジトリにjjを導入（共存モード）
jj git init --colocate

# 状態確認
jj status           # git statusに相当
jj log              # 履歴をグラフ表示
jj diff             # 変更内容確認

# 変更のコミット
jj describe -m "fix: バグ修正"   # メッセージを設定
jj new                            # 新しいコミットへ移動

# 変更の参照
jj edit <change-id>               # 特定のコミットを編集
jj show <change-id>               # コミット内容を表示

# リモート操作
jj git fetch
jj git push
```

### squash ワークフロー

Jujutsu での一般的な開発スタイルは「まず全部書いてから分割」だ。

1. 親コミットをざっくりした内容（`wip: add feature`）で作成
2. コードを書き進める（変更は自動的に現在のコミットに蓄積される）
3. `jj squash` で変更を親コミットへ押し込む
4. `jj split` でコミットを複数の論理単位に分割する
5. `jj absorb` でコード変更を自動的に適切な祖先コミットへ振り分ける

```bash
# interactiveモードでsquash（どのハンクを移動するか選択）
jj squash --interactive

# 特定のコミットへsquash
jj squash --into <commit-id>

# コミットを分割（エディタが開く）
jj split

# 変更を祖先コミットへ自動振り分け
jj absorb
```

### megamerge ワークフロー

複数のフィーチャーブランチを同時進行する際の強力なパターン。

```bash
# 3つのブランチのトップコミット c, n, x をマージ
jj new c n x           # マージコミットを作成

# このマージの上で作業する
vim src/auth.ts
vim src/api.ts

# 変更を適切な祖先ブランチへ自動振り分け
jj absorb src/auth.ts   # src/auth.tsの変更をauth関連ブランチへ
jj absorb src/api.ts    # src/api.tsの変更をapi関連ブランチへ
```

このワークフローの利点：
- 常にすべてのブランチをマージした状態で作業するので、サプライズなマージコンフリクトが発生しにくい
- コンテキストスイッチのコストが大幅に下がる
- 小さな無関係の修正を別ブランチで行う際の手間が激減する

### GitHub との連携

```bash
# ブックマーク作成とプッシュ
jj bookmark create my-feature -r @   # 現在のコミットにブックマーク作成
jj git push -b my-feature            # プッシュ

# レビューコメントへの対応（rewrite & force-push スタイル）
jj edit <commit-id>                  # 対象コミットを編集
vim src/foo.rs                       # 修正
jj describe -m "feat: 修正後のメッセージ"
jj bookmark set my-feature           # ブックマークを更新
jj git push -b my-feature            # 自動的にforce-pushになる
```

## 最新動向・未解決問題

### リリース状況（2026 年 4 月時点）

- v0.40.0 がリリース済み（GitHub Stars 28,000+）
- まだ v1.0.0 前のため、破壊的変更が入ることがある
- Git サブモジュールのサポートはまだ不完全

### Google での採用

Google は Jujutsu を内部 VCS の置き換え候補として検討・使用しており、大規模リポジトリでの実績が蓄積されつつある。

### 注目の機能追加

- `jj absorb`：変更を適切な祖先コミットへ自動振り分け（積極的に機能強化中）
- `jj file annotate`：`git blame` 相当の機能（v0.24 で追加）
- megamerge ワークフローのサポート向上

### 未解決の課題

- Git サブモジュールの完全サポート
- GUI ツールのエコシステム（現在はほぼ CLI のみ）
- `jj` の「ブックマーク」概念が Git ユーザーには最初直感的でない
- GitHub Actions などの CI 環境での統合パターンが確立中

## 関連トピック

- **Mercurial（hg）**：revset、匿名ブランチなど多くの概念の元祖。Jujutsu は Mercurial の良いところを引き継いでいる。
- **Pijul / Darcs**：パッチ理論に基づく VCS。ファーストクラスのコンフリクト処理の発想元。
- **Sapling（Facebook/Meta）**：Facebook が開発した Mercurial ベースの VCS。大規模モノレポ向け。
- **Gerrit**：Google の提案レビューシステム。Jujutsu の匿名ブランチ・変更ベースのワークフローは Gerrit と相性が良い。
- **gitoxide**：Rust 実装の Git ライブラリ。Jujutsu の Git バックエンドで使われている。
- **trunk-based development**：メインブランチへ直接コミットするスタイル。Jujutsu のワークフローと親和性が高い。
