# Markdoc: Stripeが開発した「データとしてのドキュメント」システム

## 概要

**Markdoc**は、Stripeが自社の膨大なドキュメント基盤を支えるために開発した、Markdownを拡張したオープンソースのマークアップ言語およびコンテンツフェデレーションシステムです。

従来のMarkdownの「シンプルさ」と、MDXのような「コンポーネント指向」の長所を併せ持ちつつ、最大の特徴として**「ドキュメントをデータ（AST）として扱う」**という設計思想（Docs as Data）を掲げています。これにより、大規模なドキュメントサイトにおいて、高い保守性、セキュリティ、そして厳格なバリデーションを実現しています。

## 背景・歴史

Stripeのドキュメントは、単なるテキストの羅列ではなく、ユーザーのAPIキーをサンプルコードに自動挿入したり、地域や設定に応じて内容を動的に変化させる「アプリケーション」に近い体験を提供しています。

以前のシステム（Rubyベース）では、文章の中に複雑なロジックが混在し、メンテナンスが困難になっていました。そこで、**「ライターはコンテンツ（Markdown）に集中し、エンジニアは構造とバリデーション（スキーマ）を管理する」**という役割分担を明確にするために開発されたのがMarkdocです。

## 核となる概念

Markdocを理解する上で重要な3つの柱があります。

### 1. タグ (Tags)
`{% tag_name attribute="value" %}` という独自の構文を使用して、Reactコンポーネントやカスタムロジックを呼び出します。MDXのようにJavaScriptを直接書くのではなく、あらかじめ定義された「タグ」を使用するため、構文が壊れにくく安全です。

### 2. ノード (Nodes)
見出し（heading）、段落（paragraph）、リンク（link）といった標準的なMarkdown要素（CommonMark）を指します。Markdocではこれらの標準要素の挙動もスキーマで上書き可能です。

### 3. スキーマ (Schema)
すべてのタグやノードに対して、「どのような属性を受け取るか」「どの子要素を許可するか」を定義するJavaScriptのオブジェクトです。これがMarkdocの強力なバリデーションの基盤となります。

## 詳細な仕組み・理論

### 抽象構文木 (AST) の活用
Markdocはコンテンツをパースして、まず純粋なデータ構造であるASTを作成します。
1. **Parse**: MarkdownをAST（JSON形式）に変換。
2. **Transform**: スキーマを適用し、ASTを「レンダリング可能なツリー」に変換。
3. **Render**: React, HTML, または独自の形式で出力。

このステップが分離されているため、サーバーサイドでパースしてASTだけをクライアントに送り、ブラウザで高速にレンダリングするといった柔軟な運用が可能です。

## 独自構造の定義とバリデーション

ユーザーが特に注目している「独自構造の定義」と「スキーマバリデーション」について詳述します。

### 1. 属性（Attributes）のバリデーション
各タグが受け取るプロパティに対して、型、必須チェック、正規表現によるパターンマッチング、デフォルト値を設定できます。

```javascript
attributes: {
  type: {
    type: String,
    default: 'info',
    matches: ['info', 'warning', 'error'], // 許可する値を制限
    required: true
  },
  url: {
    type: String,
    matches: /^https?:\/\// // 正規表現によるチェック
  }
}
```

### 2. 構造的制約（Children Constraints）
「このタグの中に何を配置できるか」をホワイトリスト形式で定義できます。これにより、ドキュメントの構造が意図しない形になるのを防ぎます。

*   **`children` プロパティ**: `['paragraph', 'tag']` のように、許可するノードやタグを指定します。
*   **`selfClosing: true`**: 子要素を持たせない（`{% image /%}` 形式）ことを強制します。

### 3. 動的バリデーション (`validate` 関数)
より複雑なルールが必要な場合、`validate` 関数を実装して、ASTの構造を直接チェックできます。
*   「このタグの中には必ず1つの見出しが必要」
*   「特定の属性がAの場合、子要素にBタグを含めてはならない」
といった高度なビジネスルールをビルド時に検証可能です。

## MDXとの比較：Docs as Data vs Docs as Code

| 項目 | Markdoc | MDX |
| :--- | :--- | :--- |
| **思想** | Docs as Data (宣言的) | Docs as Code (命令的) |
| **セキュリティ** | **極めて高い**。JSを直接実行させない。 | **注意が必要**。任意のJSXが実行可能。 |
| **バリデーション** | スキーマによる強力な静的検証。 | 柔軟だが、実行時エラーになりやすい。 |
| **パフォーマンス** | ASTがJSON化可能で、シリアライズが容易。 | JSとしてコンパイルが必要でビルドが重くなりがち。 |
| **ターゲット** | 大規模チーム、非エンジニアのライター。 | 開発者個人、小〜中規模のReactプロジェクト。 |

## 具体例・応用事例

### Stripeのドキュメント
世界最高峰と言われるStripeのAPIドキュメントの裏側はすべてMarkdocで構築されています。複数のプログラミング言語のタブ切り替え、パーソナライズされたサンプルコード、サイドバーの自動生成などがスキーマベースで管理されています。

### ユーザー投稿コンテンツの安全なレンダリング
MDXと違い、Markdocは「実行可能なコード」を含まないため、CMSやユーザーが投稿するMarkdownを安全にコンポーネント化して表示する用途に非常に適しています。

## 最新動向・未解決問題
Next.jsとの公式統合が進んでおり、`@markdoc/next.js` を使用することで、`.md` ファイルをそのままページとして扱うことが容易になっています。一方で、エコシステムはMDX（remark/rehype）ほど巨大ではないため、既存のMarkdownプラグインをそのまま流用できないケースがあるのが課題です。
